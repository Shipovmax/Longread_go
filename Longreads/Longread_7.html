01

Контекст

Контекст помогает дирижировать программой, у которой горутин много. О нём можно думать на трёх уровнях: бытовом — как об окружении, задающем точный смысл происходящего; практическом — как о типе данных, управляющем жизненным циклом горутин (а значит, и всей программы); и техническом — это просто интерфейс, которому может удовлетворять любой тип.

Контекст умеет три важные вещи: передавать сигнал отмены между горутинами, управлять дедлайнами выполнения кода и нести метаданные сквозь слои кодовой базы. Без него не получилось бы аккуратно передавать метаданные при HTTP/gRPC-запросах, контролировать время ответа сервисов и БД, не терять ресурсы на зависших фоновых задачах.

context.gogo
type Context interface {
	Deadline() (deadline time.Time, ok bool)
	Done() <-chan struct{}
	Err() error
	Value(key interface{}) interface{}
}
Deadline()
время, к которому контекст должен быть отменён, и флаг — установлен ли дедлайн вообще.
Done()
канал, закрывающийся в момент отмены контекста.
Err()
причина отмены как ошибка.
Value(key)
значение из контекста по ключу.

Типы контекста

Пакет context даёт готовые конструкторы для создания контекстов на лету:

КонструкторЧто делает
context.Background()пустой контекст — стартовая точка для любой цепочки
context.TODO()тоже пустой, но заглушка на время, пока не решено, нужен ли контекст вообще
context.WithCancel(ctx)контекст + функция ручной отмены — закрывает Done() по вызову
context.WithTimeout(ctx, d)закрывается сам по истечении d, либо раньше через cancel
context.WithDeadline(ctx, t)закрывается по достижении конкретного момента времени t
// правило №1

Background — начальная точка для целых цепочек контекстов. TODO в продакшене не используется никогда — это заглушка для мест, куда позже подставится настоящий контекст.

WithTimeout под капотом обращается к WithDeadline (исходник) — приятный пример переиспользования кода. Ещё есть context.AfterFunc(ctx, func(){...}), выполняющая замыкание после завершения контекста, и методы с постфиксом Cause, позволяющие приложить бизнес-причину отмены:

main.gogo
ctx, cancel := context.WithCancelCause(context.Background())

go func() {
	time.Sleep(200 * time.Millisecond)
	cancel(errors.New("client closed browser tab"))
}()

<-ctx.Done()
fmt.Println("Err:", ctx.Err())            // context canceled
fmt.Println("Cause:", context.Cause(ctx)) // client closed browser tab

Иерархии контекстов

Из контекстов строятся целые цепочки — большинство конструкторов сами принимают контекст и оборачивают его:

main.gogo
ctx := context.Background()
ctx, cancel = context.WithCancel(ctx)
ctx, cancel = context.WithTimeout(ctx, 5*time.Second)

Переменная переиспользуется потому, что под капотом это структуры-обёртки, каждая из которых хранит внутри себя интерфейс Context — а значит, может обернуть любую кастомную реализацию.

flowchart TB
  BG["Background"] --> WC["WithCancel"] --> WT["WithTimeout"] --> WV["WithValue"]
  WV -.->|"отмена течёт только вниз по цепочке"| BLOCKED["отмена дочернего
НЕ отменяет родителя"]

Отмена родителя отменяет всех детей; отмена ребёнка родителя не касается

// правило №2

Отменился родительский контекст — отменяются и дочерние. Отменился дочерний — родительский живёт дальше. Исключение — context.WithoutCancel(ctx): возвращает дочерний контекст, независимый от отмены родителя. Пригождается, когда операция обязана довыполниться, что бы ни случилось выше по цепочке.

Передача значений в контексте

Контекст умеет быть контейнером для передачи данных между слоями — метаданных, авторизации и прочего сопровождения запроса:

main.gogo
ctx := context.WithValue(ctx, key, value)

И ключ, и значение — пустой интерфейс; под капотом (исходник) это снова структура в структуре, вложенная иерархия по ключам.

// никогда не делай так

Параметры бизнес-логики через контекст передавать нельзя. Причин три:

1

Неявный контракт. Знает ли принимающая сторона, что важные данные лежат в контексте? А если знает — точно ли они там окажутся?

2

Производительность поиска. Вложенные контексты ищутся по цепочке за O(n) — в худшем случае обход всей иерархии.

3

Стоимость приведения типа. ctx.Value отдаёт any, а значит, каждый раз нужен type assertion — и нет гарантии, что тип совпадёт.

main.gogo
if id, ok := ctx.Value(requestIDKey).(string); ok {
	fmt.Println(id)
} else {
	log.Fatal("fatal!!!")
}

Если метаданные всё же нужно передать — заводи ключ кастомным типом-константой, чтобы случайно не столкнуться с чужим ключом:

main.gogo
type contextKey string // кастомный тип ключа на основе строк

const userIDKey contextKey = "userID"

ctx := context.WithValue(context.Background(), userIDKey, 123)

Работа с контекстом

main.gogo
func worker(ctx context.Context, id int) {
	for {
		select {
		case <-ctx.Done():
			fmt.Printf("Worker %d: остановка, причина: %v\n", id, ctx.Err())
			return
		default:
			fmt.Printf("Worker %d: работает...\n", id)
			time.Sleep(500 * time.Millisecond)
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())

	for i := 1; i <= 3; i++ {
		go worker(ctx, i)
	}

	time.Sleep(2 * time.Second)

	fmt.Println("main: отправляем сигнал отмены...")
	cancel()

	time.Sleep(1 * time.Second)
	fmt.Println("main: программа завершена")
}

Три воркера крутятся в бесконечном цикле, слушая Done() через неблокирующий select с default. Как только main вызывает cancel(), все три получают сигнал и корректно завершаются.

// всегда

Для контекстов с отменой функцию cancel нужно вызывать всегда — обычно через defer, иначе рискуешь получить утечку памяти и горутин:

ctx, cancel := context.WithCancel(context.Background())
defer cancel()

Ошибки из пакета context тоже можно проверять явно:

main.gogo
if err := ctx.Err(); err != nil {
	if errors.Is(err, context.Canceled) {
		// ...
	}
	if errors.Is(err, context.DeadlineExceeded) {
		// ...
	}
}

Идиоматика при работе с контекстом

1

Контекст — всегда первый параметр функции: сразу видно, что она умеет в отмену или тайм-аут.

2

Контекст не хранят в структурах — он не имеет отношения к их жизненному циклу.

3

В долгих операциях контекст проверяют через Done() в неблокирующем select.

4

Следи за тайм-аутами: дочерний контекст с тайм-аутом больше родительского может повести себя неожиданно.

5

context.TODO в рабочем коде не нужен — он ничего не делает и лишь отвлекает от сути.

6

context.Background создаётся только на самом верхнем уровне — не обрывай цепочку контекстов новым Background посередине.

02

Graceful shutdown

Ctrl+C обрывает программу мгновенно. Но что, если перед выходом нужно закрыть соединения с БД или дописать на диск незавершённые вычисления? Для этого — graceful shutdown: способность приложения корректно завершиться, сохранив целостность данных и не оборвав критические операции на середине.

ОС, Docker и Kubernetes общаются с программой через сигналы. В Go их слушают через пакет os/signal:

СигналНомерСмысл
SIGINT2прерывание, обычно Ctrl+C
SIGTERM15«вежливый» запрос на завершение — время на уборку есть
SIGKILL9принудительное завершение — не перехватывается, крайняя мера
SIGHUP1исторически «обрыв терминала», сегодня чаще — перезагрузка конфига
main.gogo
func main() {
	// Буферизированный — чтобы отправка сигнала не заблокировалась
	sigChan := make(chan os.Signal, 1)

	signal.Notify(sigChan,
		syscall.SIGINT,  // Ctrl+C
		syscall.SIGTERM, // Сигнал завершения от системы/Kubernetes
		syscall.SIGHUP,  // Сигнал перезапуска конфигурации
	)

	fmt.Println("Приложение запущено. Ожидаю сигналы...")

	go func() {
		for i := 1; i <= 10; i++ {
			fmt.Printf("Выполняю работу %d/10...\n", i)
			time.Sleep(2 * time.Second)
		}
	}()

	sig := <-sigChan // Блокируемся до получения сигнала
	log.Printf("Получен сигнал: %v (%v)\n", sig, sig)
}

А вот так это выглядит для настоящего HTTP-сервера (о самом HTTP — в следующей главе, здесь важен именно паттерн):

main.gogo
func gracefulServer() {
	server := &http.Server{
		Addr:    ":8080",
		Handler: createRouter(),
	}

	go func() {
		if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			log.Printf("Ошибка сервера: %v", err)
		}
	}()

	sig := make(chan os.Signal, 1)
	signal.Notify(sig, syscall.SIGINT, syscall.SIGTERM)
	<-sig

	log.Println("Получен сигнал завершения, начинаем graceful shutdown...")

	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()

	if err := server.Shutdown(ctx); err != nil {
		log.Printf("Ошибка при shutdown: %v", err)
		server.Close() // Вынужденное завершение
	}

	log.Println("Сервер корректно завершён")
}
03

Примитивы синхронизации

Каналы, уже знакомые тебе, — не единственный примитив синхронизации: низкоуровневый инструмент, который защищает общие ресурсы от гонок при конкурентном доступе. Остальные живут в пакетах sync и atomic.

Атомики

Максимально низкоуровневый примитив — обёртка прямо над ассемблером (исходник). Атомарная операция гарантированно не прерывается и синхронизируется на уровне инструкций процессора — доступ к переменной гарантированно эксклюзивен в момент операции. Чаще всего это потокобезопасный счётчик:

main.gogo
func main() {
	var v int64 = 0

	go atomic.AddInt64(&v, 1)
	go atomic.AddInt64(&v, -2)

	time.Sleep(1 * time.Second)

	val := atomic.LoadInt64(&v)
	fmt.Println(val)
}

Без гарантии порядка выполнения этих двух горутин мы всё равно гарантированно получаем корректный, непротиворечивый результат.

Мьютексы

Мьютекс защищает блок кода от неконсистентного состояния при доступе из нескольких горутин — например, когда одна горутина пишет в мапу, а другая в этот же момент её меняет. В исходниках это тоже структура:

main.gogo
func exampleOne() {
	mu := sync.Mutex{}

	mu.Lock()
	fmt.Println("Mutex locked")
	mu.Unlock()
}
// идиоматическая договорённость

Поле с мьютексом принято располагать прямо над тем, что оно защищает — чисто визуальное соглашение, но оно того стоит:

main.gogo
type Cache struct {
	mu sync.Mutex // Мьютекс защищает мапу ниже
	m  map[int]int

	sl []int // Слайс — вне защиты мьютекса
}

func (c *Cache) Add(key int, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()

	c.m[key] = val
}

defer здесь почти всегда к месту — гарантирует разблокировку при любом сценарии выхода из функции.

У обычного мьютекса есть родственник — RWMutex, с методами RLock/RUnlock:

MutexRWMutex
Блокирует чтениеда, всегдатолько если идёт запись
Блокирует записьда, всегдада, всегда — блокирует и читателей тоже

RWMutex стоит предпочесть, когда чтений заметно больше, чем записей.

WaitGroup

Позволяет дождаться завершения заранее известного числа горутин. Внутри — тоже структура, реализованная поверх атомиков (исходник), а методов у неё всего три:

Add(n)
увеличивает счётчик ожидаемых горутин.
Done()
декрементирует счётчик по завершении одной горутины.
Wait()
блокирует выполнение, пока счётчик не дойдёт до нуля.
flowchart LR
  A["wg.Add(n)"] --> B["запускаем n горутин"]
  B --> C["каждая по завершении:
defer wg.Done()"]
  C --> D{"счётчик == 0?"}
  D -- нет --> C
  D -- да --> E["wg.Wait() разблокируется"]

Add задаёт счётчик, Done его уменьшает, Wait блокируется до нуля

main.gogo
func main() {
	var wg sync.WaitGroup

	wg.Add(2)

	for range 2 {
		go func() {
			defer wg.Done()
			fmt.Println("Hello World")
		}()
	}

	wg.Wait()
}
// осторожно

Запускай ровно столько горутин, сколько указано в Add — иначе рискуешь поймать deadlock. И держи в уме: обработка ошибок с голым WaitGroup превращается в отдельную головную боль — для этого есть errgroup, который заодно и ошибки собирает, и горутины корректно завершает.

Once

Структура с методом Do, гарантирующая, что функция выполнится только один раз — первой добравшейся до неё горутиной, остальные вызовы просто ничего не делают:

main.gogo
var once sync.Once

func initialize() {
	fmt.Println("Инициализация ресурсов (выполняется один раз)...")
}

func main() {
	var wg sync.WaitGroup

	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()

			once.Do(initialize)
			fmt.Printf("Горутина %d завершила работу\n", id)
		}(i)
	}

	wg.Wait()
	fmt.Println("Программа завершена.")
}

sync.Map

Потокобезопасная мапа из коробки (исходник) — под капотом мьютекс плюс две обычные мапы: для актуальных и изменённых данных. Но она заметно медленнее и неуклюжее ручной связки «мапа + мьютекс» — профит появляется только при куче свободных ядер и подавляющей доле операций чтения.

Прочие примитивы

Используются заметно реже, но стоит знать об их существовании — стоит изучить самостоятельно:

sync.Cond sync.OnceFunc sync.Pool poolqueue (внутренний)
04

Паттерны конкурентности

У многопоточного стиля программирования, как и у любого другого, есть свой набор устоявшихся классов задач и обобщённых решений — паттернов.

Singleflight

Группирует одновременные запросы к одной и той же долгой операции: появляется «лидер», который реально её выполняет, и пул ожидающих — как только лидер завершается, результат достаётся всем сразу. Это экономит ресурсы сервера при всплеске одинаковых запросов во время долгих вычислений. Реализован в расширенной стандартной библиотеке — golang.org/x/sync/singleflight.

// как устроено

call хранит результат и канал done, закрывающийся по завершении. Мьютекс здесь разблокируется дважды подряд вручную, а не через defer: единственный defer Unlock держал бы блокировку всё время, пока выполняется сама операция — а этого делать нельзя, она может быть долгой.

singleflight.gogo
type call struct {
	err   error
	value any
	done  chan struct{}
}

type SingleFlight struct {
	mutex sync.Mutex
	calls map[string]*call
}

func NewSingleFlight() *SingleFlight {
	return &SingleFlight{calls: make(map[string]*call)}
}

func (s *SingleFlight) Do(ctx context.Context, key string, action func(context.Context) (any, error)) (any, error) {
	s.mutex.Lock()
	if call, found := s.calls[key]; found {
		s.mutex.Unlock()
		return s.wait(ctx, call) // Вызов уже идёт — просто встаём в очередь на результат
	}

	call := &call{done: make(chan struct{})}
	s.calls[key] = call
	s.mutex.Unlock()

	go func() {
		defer func() {
			if v := recover(); v != nil {
				call.err = errors.New("error from single flight")
			}
			close(call.done)

			s.mutex.Lock()
			delete(s.calls, key)
			s.mutex.Unlock()
		}()

		call.value, call.err = action(ctx)
	}()

	return s.wait(ctx, call)
}

func (s *SingleFlight) wait(ctx context.Context, call *call) (any, error) {
	select {
	case <-ctx.Done():
		return nil, ctx.Err()
	case <-call.done:
		return call.value, call.err
	}
}

Генератор

Порождает данные и владеет полным жизненным циклом канала, в который их пишет — включая закрытие:

main.gogo
func generator() <-chan int {
	ch := make(chan int)

	go func() {
		for i := range 10 {
			ch <- i + 1
		}
		close(ch)
	}()

	return ch
}

Fan-in: несколько источников сливаются в один канал

Fan-in

Собирает данные из нескольких каналов в один — удобно, когда результаты нескольких горутин нужно свести в одной точке:

main.gogo
func fanIn(input1, input2 <-chan string) <-chan string {
	ch := make(chan string)

	go func() {
		for {
			select {
			case s := <-input1:
				ch <- s
			case s := <-input2:
				ch <- s
			}
		}
	}()

	return ch
}
flowchart LR
  CH["ch"] --> W1["worker 1"]
  CH --> W2["worker 2"]
  CH --> W3["worker 3"]

Fan-out: один источник раздаёт работу нескольким получателям

Fan-out

Делает обратное — распределяет данные одного канала между несколькими воркерами. Хорошо сочетается с генератором:

main.gogo
func worker(ch <-chan int, wg *sync.WaitGroup) {
	defer wg.Done()

	for v := range ch {
		fmt.Println(v)
		time.Sleep(1 * time.Second)
	}
}

func sender() {
	ch := make(chan int)
	var wg sync.WaitGroup

	for i := 0; i < 2; i++ {
		wg.Add(1)
		go worker(ch, &wg)
	}

	for i := range 10 {
		ch <- i
	}

	close(ch)
	wg.Wait()
	fmt.Println("done")
}

consumer"]

Pipeline: каждая стадия — отдельная горутина со своим каналом на входе и выходе

Pipeline

Выстраивает конвейер обработки — например, последовательную трансформацию потока данных или файлов:

main.gogo
func producer() <-chan int {
	c := make(chan int)

	go func() {
		for i := range 10 {
			c <- i + 1
		}
		close(c)
	}()

	return c
}

func producerConsumer(c <-chan int) <-chan int {
	out := make(chan int)

	go func() {
		for v := range c {
			out <- v * 2
		}
		close(out)
	}()

	return out
}

func consumer(ch <-chan int) {
	for v := range ch {
		fmt.Println(v)
	}
}

Worker pool: фиксированный пул воркеров разбирает общую очередь задач

Worker pool

Организует параллельную обработку однотипной работы фиксированным числом воркеров — типичный выбор для больших объёмов однородных данных:

main.gogo
func worker(jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
	defer wg.Done()

	for j := range jobs {
		time.Sleep(1 * time.Second)
		fmt.Println("job", j)
		results <- j * j
	}
}

func main() {
	jobs := make(chan int)
	results := make(chan int)

	var wg sync.WaitGroup

	for i := range 3 {
		wg.Add(1)
		go worker(jobs, results, &wg)
	}

	go func() {
		for i := range 10 {
			jobs <- i
		}
		close(jobs)
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	for result := range results {
		fmt.Println(result)
	}
}
