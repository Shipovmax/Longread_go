01

Зачем нужен тулинг

«У меня локально работает, ничего не знаю, проблема на вашей стороне» — не совсем шутка. Код должен не просто компилироваться: он обязан быть читаемым для коллег, предсказуемым в сопровождении и защищённым от типичных ошибок. Хорошая новость — Go идёт с уже выстроенной экосистемой инструментов для этого.

Тулинг помогает держать единое оформление кода при параллельной разработке, ловить подозрительные конструкции, которые пропускает сам компилятор, чистить импорты и дублирование, находить проблемы с конкурентностью и зависимостями. Ручная проверка такого не гарантирует — а вот автоматизация справляется стабильно.

flowchart LR
  A["пишем код"] --> B["форматируем"] --> C["статические проверки"] --> D["тесты"] --> E["коммитим на ревью"]

Стандартный пайплайн подготовки кода перед тем, как отдать его коллегам

ИнструментТипЧто делает
gofmtвстроенныйприводит код к единому стилю оформления
go testвстроенныйзапускает тесты пакета/проекта
go vetвстроенныйловит подозрительные, но валидные конструкции
go docвстроенныйпоказывает документацию по коду
goplsвнешнийlanguage-сервер — подсказки прямо в редакторе
goimportsвнешнийgofmt + автоматическая чистка импортов
golangci-lintвнешнийагрегатор десятков линтеров под одной командой
govulncheckвнешнийпроверяет зависимости на известные уязвимости

Внешние инструменты ставятся через go install:

терминалbash
go install golang.org/x/tools/gopls@latest
go install golang.org/x/tools/cmd/goimports@latest
go install golang.org/x/vuln/cmd/govulncheck@latest
// про @latest

После @ лучше писать конкретную версию инструмента. @latest оправдан, только если ты сознательно хочешь самую свежую версию и уверен в её совместимости с остальным окружением.

02

Встроенный тулинг Golang

Форматирование кода

В Go о форматировании не спорят — достаточно вызвать gofmt. Он расставляет отступы, переносы и выравнивание одинаково для всех, так что чужой код читается в привычном формате:

терминалbash
go fmt ./...     # весь текущий пакет и поддиректории
gofmt -w file.go # конкретный файл, -w — записать изменения
gofmt -w .       # весь проект

Под капотом код разбирается в древовидную структуру, похожую на AST, а затем собирается обратно по правилам gofmt. Один из постулатов Go посвящён именно этому: «Gofmt's style is no one's favorite, yet gofmt is everyone's favorite». Большинство IDE вызывают форматер сами при сохранении — если твоя нет, стоит настроить это вручную.

// gofmt vs go fmt

go fmt — просто обёртка, вызывающая gofmt для всего текущего пакета.

Более умное форматирование

gofmt не трогает импорты — забытые, лишние, неотсортированные. Для этого — goimports: она и сама чистит импорты, и форматирует код точно так же, как gofmt:

терминалbash
goimports -w main.go # конкретный файл
goimports -w .       # весь проект

Без флага -w результат просто печатается в консоль, а не записывается в файл.

Помощь прямо в редакторе

gopls («Go please») — language-сервер для Go: работает не после написания кода, а во время. Даёт подсветку ошибок, переход к определению, поиск использований, автодополнение и подсказки прямо в IDE.

// без него никак

Редактор без gopls — не лучший выбор для Go. Он ловит проблемы ещё до запуска тестов и линтеров — если у тебя не VS Code/Goland с настройками из коробки, проверь, что gopls действительно подключён.

Очищение кода от подозрительных вещей

go vet ищет не стилевые, а логические подозрительности — код, который компилируется, но выглядит как ошибка: бесполезные объявления переменных, типичные промахи с sync/atomic, неиспользуемый код и другое (полный список — в документации).

терминалbash
go vet ./...

Важно: go vet не гарантирует отсутствие проблем — он лишь подсвечивает подозрительные паттерны.

Линтеры

Всё вышеперечисленное — тоже линтеры, просто базовые. Индустриальный стандарт для более серьёзных проверок — golangci-lint: точка входа сразу для набора линтеров, настраиваемая через YAML, быстрая, с готовой интеграцией в CI.

.golangci.ymlyaml
run:
  timeout: 5m
  modules-download-mode: readonly

linters:
  disable-all: true # Отключить всё по умолчанию
  enable:            # Что включено принудительно
    - errcheck      # Проверка необработанных ошибок
    - goimports     # Проверка импортов
    - govet         # Тот самый go vet!
    - staticcheck   # Статический анализ
    - unused        # Неиспользуемый код
    - gosimple      # Упрощение кода
    - bodyclose     # Закрытие http тел
    - dupl          # Поиск дублирования кода
    - reassign      # Поиск переопределения переменных
    - unconvert     # Лишние приведения типов

issues:
  exclude-use-default: false # Не использовать стандартные исключения
  max-issues-per-linter: 0   # Показать все ошибки
  max-same-issues: 0         # Показать все похожие ошибки
  exclude-rules:
    - path: _test\.go
      linters:
        - goconst   # Игнорировать дублирование строк в тестах

Плохой подход

  • Включать все линтеры подряд без разбора
  • Гасить сотни предупреждений директивой //nolint
  • Чинить линтером код вместо того, чтобы его улучшать

Лучше делать так

  • Выбирать только проверки, полезные тебе и команде
  • Со временем отключать правила без реальной ценности
  • //nolint — только в действительно исключительных случаях

Линтеры — ещё один гарант качества кода в подавляющем большинстве компаний, так что с ними стоит научиться жить.

Тестирование кода

Тесты — тоже часть тулинга, а не отдельная тема в стороне. Правило простое: если после изменения тесты не запущены — задача не доделана. Отдельно стоит флаг -race: тесты асинхронного кода без него не гарантируют отсутствия гонок данных.

Проверка зависимостей

Даже идеальный собственный код не спасает от уязвимостей в чужих зависимостях. govulncheck сканирует go.mod и проверяет не просто наличие уязвимой библиотеки в импортах, а реально ли используется уязвимый код — прямо или косвенно:

терминалbash
govulncheck ./...

Работает и с исходным кодом, и с бинарниками, опираясь на базу известных уязвимостей vulndb. Сторонние библиотеки тоже пишут люди — и им тоже свойственно ошибаться.

Чек-лист перед PR

терминалbash
gofmt -w .
go vet ./...
golangci-lint run
go test ./...
go test -race ./...
govulncheck ./...

Дальше остаётся только убедить ревьюера, что код делает ровно то, что требовалось. Полезные вопросы к себе перед отправкой:

  • Читается ли код без устного объяснения?
  • Понятны ли все названия переменных, методов и функций?
  • Обработаны ли все ошибки?
  • Нет ли лишних абстракций?
  • Помогают ли комментарии или только мешают?
03

Идиоматичный код на Go

Помимо Go Proverbs, авторитетными ориентирами (необязательными, но проверенными часами разработки) считаются стайлгайды Google и Uber — двух компаний, сильнее прочих повлиявших на go-комьюнити. Ниже — то, что стоит усвоить в первую очередь; остальное — по ссылкам в источниках.

Названия методов и функций

Ключевое правило: не повторяй имя пакета в именах его сущностей.

плохоdb
package db

func CreateDbConnection() (*DbConn, error) {}

// снаружи: db.CreateDbConnection()
хорошоdb
package db

type Conn struct{}

func CreateConn() (*Conn, error) {}

// снаружи: db.CreateConn()

Пакет уже говорит, кто он и за что отвечает — повторять это в имени функции значит читать одно и то же слово дважды.

Геттеры в Go тоже не приняты — Get не добавляет смысла, когда мы и так запрашиваем данные у структуры:

плохо
func (u User) GetAddress() string {
	return u.Address
}
// address := user.GetAddress()
хорошо
func (u User) Address() string {
	return u.Address
}
// address := user.Address()

Исключение — совпадение имени пакета с его главной сущностью: package user с типом User внутри — норма, ведь других вариантов там особо и нет.

Наименование пакетов

Имя пакета — максимально короткое, без _. Два слова — слитно: package userinfo. Имя не должно совпадать с именами переменных, которые обычно заводят при импорте — если конфликт неизбежен, используй осмысленный алиас: import usersrv "github.com/.../user".

// главное правило

Никогда не называй пакеты обезличенно: utils, common, helper, model. По такому имени невозможно понять зону ответственности. Пакет со специфичными функциями лучше назвать по области применения: auth, userinfoconvert, mocks.

Ещё раз об интерфейсах

Интерфейсы отлично работают как входные параметры — сигнатуре важно только поведение, а не конкретный тип. Интерфейс с одним методом принято называть по этому методу: Reader, Writer, Seeker.

объявлен в месте реализации
package format

type Formatter interface {
	Format() string
}

// пакет example всё равно тащит
// весь пакет format целиком
объявлен в месте использования
package example

type Formatter interface {
	Format() string
}

func example(f Formatter) {
	f.Format()
}

Второй вариант не тащит лишних импортов и абстрагирует логику по-настоящему. И ещё: возвращать интерфейсы из функций в Go не принято — исключения редки, но бывают (например, когда действительно нужен именно io.Reader, а не его конкретная реализация — как правило, ради цепочки ожидаемого поведения).

nil-мапы и слайсы

len() спокойно работает и с неинициализированными мапами/слайсами, просто возвращая 0 — поэтому вместо двух проверок достаточно одной:

main.gogo
func AnyDo() {
	var sl []int

	if len(sl) == 0 { // Эквивалентно проверке sl == nil
		return
	}
}

Инициализировать мапы и слайсы хорошим тоном считается через var, а не sl := []int{} — так меньше путаницы между «пока не существует» и «существует, но пуст», а len() в обоих случаях всё равно скажет правду.

// два неписаных правила

Запуская горутину, сразу понимай, где и при каких условиях она завершится — иначе рискуешь утечкой горутин и OOM Killer'ом в проде. И если без горутины можно обойтись — обойдись: непредсказуемое, сложно тестируемое поведение того не стоит.

Каналы

По умолчанию — небуферизированный канал. Буфер добавляй только тогда, когда точно понимаешь, что он не усложняет логику и реально ускоряет обработку. И не забывай про направленные каналы — они ограничивают функциональность методов пакета, страхуя от неожиданного использования.

Параметры функций

Сигнатура с восемью параметрами читается плохо:

было
func Example(one int, two string, three uint, four, five uuid.UUID,
	six any, seven string, eight bool) (map[int]string, uint, []int, any, error) {}

Для сложных сигнатур — структуры на вход и на выход:

стало
type ExampleRequest struct {
	One   int
	Two   string
	Three uint
	Four, Five uuid.UUID
	Six   any
	Seven string
	Eight bool
}

type ExampleResp struct{ /* ... */ }

func Example(req ExampleRequest) (ExampleResp, error) {}

Ошибки, паники, дженерики, глобальные переменные

Кратко о главном

  • Обрабатывай ошибки всегда и добавляй контекст, где это уместно
  • Не паникуй без необходимости — лучше отдать ошибку, чем уронить сервис
  • Не используй дженерики «на будущее» — только когда универсальность реально нужна сейчас
  • Глобальных переменных избегай — они рушат консистентность состояния; глобальная константа куда безопаснее
