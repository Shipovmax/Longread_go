01

Файлы конфигураций и теги структур

Флаги командной строки хороши для CLI-утилит, но настоящему сервису нужно куда больше данных при старте: URL сторонних сервисов, ключи БД, тайм-ауты, настройки кешей, уровни логирования — и всё это отдельно для локали, stage и прода.

Сериализация
объект превращается в формат для хранения/передачи: struct → JSON/YAML, json.Marshal.
Десериализация
обратный процесс: JSON/YAML → struct, json.Unmarshal.

JSON

JavaScript Object Notation — текстовый формат из пар ключ:значение, разделённых запятыми (кроме последней). Значения — строки, числа, bool, null, вложенные объекты или массивы. Лёгкий, читаемый, стандарт де-факто в современной разработке:

config.jsonjson
{
	"port": ":8080",
	"log_level": 2
}

YAML

Ещё более дружелюбный к человеку формат — та же концепция «ключ:значение», но иерархия задаётся отступами, без скобок и запятых. Часто предпочтителен именно для конфигов, легко конвертируется в JSON и обратно, а в отличие от него поддерживает комментарии:

config.yamlyaml
server:
    port: 8080
    host: localhost
app:
    log_level: 2
    enabled_test: true

test: null
dev: ["local", "stage", "prod"]

localhost без кавычек всё равно распознаётся как строка. Явную типизацию можно задать через !![тип]:

config.yamlyaml
this_is_string: !!str 67.43

YAML умеет и в переиспользование значений — через якоря (&) и алиасы (*):

config.yamlyaml
default: &default_settings
    port: 8080

local:
    <<: *default_settings
    host: localhost
// .yml vs .yaml

Оба расширения равноправны — .yml родом из эпохи трёхбуквенных расширений, сегодня предпочтительнее .yaml.

Теги структур

Чтобы конфиг ложился в структуру без ручного разбора, полям нужны теги — строковые метаданные, читаемые через рефлексию:

main.gogo
type Config struct {
	Port int    `json:"port" yaml:"port"`
	Host string `json:"host" yaml:"host"`
}

Одно поле может нести сразу несколько тегов, а имя тега вовсе не обязано совпадать с именем поля. encoding/json сериализует только экспортируемые поля — на неэкспортируемое хоть вешай тег, пакет его не увидит:

main.gogo
type Config struct {
	Port int    `json:"port" yaml:"port"`
	host string `json:"host" yaml:"host"` // Не сериализуется, даже с тегом
}

Тегом управляется куда больше, чем просто имя ключа:

main.gogo
type User struct {
	Name     string `json:"name"`             // Обычный случай
	Surname  string `json:"last_name"`        // Имя поля и тега различаются
	Age      int    `json:"age,omitempty"`    // Пропустить при нулевом значении
	Password string `json:"-"`                // Исключить из сериализации совсем
	Address  string `json:",omitempty"`       // Имя ключа = имя поля + omitempty
	HasJob   bool   `json:"has_job,omitzero"` // omitzero — см. ниже
}
-
поле полностью исключается из JSON, в обе стороны.
,omitempty
пропускает zero value — но только те типы, которые умеет распознать сам механизм.
,omitzero
то же самое, но шире: убирает нулевые значения и там, где omitempty бессилен — например, у time.Time{}.

JSON-объекты в Go живут как слайс байт до момента сериализации/десериализации в структуру:

main.gogo
response := answer{Key: "value"}

b, err := json.Marshal(response) // struct → []byte
if err != nil {
	panic(err)
}
fmt.Println(string(b)) // {"key":"value"}

k := answer{}
err = json.Unmarshal(b, &k) // []byte → struct
if err != nil {
	panic(err)
}

  S["struct Config"] -->|json.Marshal / yaml.Marshal| B["[]byte
{...} или YAML-текст"]
  B -->|json.Unmarshal / yaml.Unmarshal| S

Сериализация и десериализация — путь туда и обратно между структурой и байтами

С YAML сложнее: сам Go нативной поддержки не имеет. Раньше использовался go-yaml — сейчас архивирован (что не значит «нельзя использовать», просто зафиксирован в стабильном состоянии), развитие продолжилось в форке, есть и альтернатива — goccy/go-yaml.

YAML-теги похожи на JSON, но добавляют свой — inline, встраивающий структуру в структуру при сериализации (не все библиотеки делают это автоматически):

main.gogo
type HTTPConfig struct {
	Host string `yaml:"host"`
	Port int    `yaml:"port"`
}

type Config struct {
	HTTPConfig `yaml:",inline"`
	Debug      bool `yaml:"debug"`
}
main.gogo
type Config struct {
	Server   ServerConfig   `yaml:"server"`
	Database DatabaseConfig `yaml:"database"`
}

func main() {
	yamlFile, err := os.ReadFile("config.yaml")
	if err != nil {
		log.Fatalf("Ошибка чтения файла: %v", err)
	}

	var config Config
	if err := yaml.Unmarshal(yamlFile, &config); err != nil {
		log.Fatalf("Ошибка парсинга: %v", err)
	}

	fmt.Printf("Сервер запущен на %s:%d\n", config.Server.Host, config.Server.Port)
}
// на заметку

Структуры с одинаковыми полями, но разными тегами — разные типы, их нельзя сравнить через ==, пока теги не совпадут. И ещё: тег — просто метаданные, он никак не участвует в логике приложения сам по себе.

JSON vs YAML: строгий машинный формат без лишнего — бери JSON; большой конфиг, который часто редактируют руками, — YAML.

02

Переменные окружения

Переменные окружения — пары key=value, которые хранит ОС вне кода программы. Это не фича Go, а общий механизм среды исполнения — потому он одинаково удобен и локально, и в Docker/Kubernetes, и для голого бинарника. Twelve-Factor App, методология Heroku для облачных SaaS-сервисов, прямо рекомендует хранить конфигурацию, меняющуюся между деплоями, именно в окружении, а не в коде.

меняются без пересборки не привязаны к языку/платформе секреты не лежат в исходниках

Это ещё и снижает риск закоммитить чувствительные настройки в репозиторий и упрощает масштабирование. Кстати, посмотреть Go-специфичные переменные среды можно командой go env прямо в терминале.

main.gogo
fmt.Println(os.Getenv("APP_PORT")) // "" если переменной нет
// Getenv vs LookupEnv

os.Getenv молча вернёт пустую строку, если переменной нет — не отличишь «нет значения» от «значение пустое». os.LookupEnv возвращает и значение, и флаг существования — используй его, если это различие важно.

Переменные окружения — всегда строки, поэтому провалидировать и привести к нужному типу нужно самостоятельно. Ошибки тут в подавляющем большинстве — не «баг в Go», а нарушенный контракт между окружением и приложением.

Для локальной разработки удобен текстовый файл .env — просто набор строк key=value. Это не стандарт языка и не само окружение — только заготовка, из которой переменные загружаются в него:

main.gogo
import "github.com/joho/godotenv"

func main() {
	godotenv.Load() // Загружает переменные из .env в систему
	val := os.Getenv("MY_VAR")
}

Когда переменных десяток, дёргать os.Getenv на каждую — рутина. Библиотека caarlos0/env раскладывает их по структуре через теги, точно так же, как encoding/json:

main.gogo
type Config struct {
	DBHost string `env:"DB_HOST"`
	DBPort int    `env:"DB_PORT"`
	APIKey string `env:"API_KEY" envDefault:"12345678"` // Значение по умолчанию
	Debug  bool   `env:"DEBUG"`
}

func main() {
	if err := godotenv.Load(); err != nil {
		log.Println("No .env file found, relying on environment variables")
	}

	cfg := Config{}
	if err := env.Parse(&cfg); err != nil {
		log.Fatalf("Error parsing env: %v", err)
	}

	fmt.Printf("Config: %+v\n", cfg)
}

.env уместен для локальной разработки и CI. В остальных случаях переменные обычно прописаны прямо в Docker-контейнере или в YAML-манифесте, который выбирается автоматически по контуру деплоя.

  • всегда в верхнем регистре;
  • с понятным префиксом приложения: APP_PORT, APP_DB_URL;
  • без слишком общих имён.
// не тот случай

Секреты и чувствительные данные в .env и подобных файлах лучше не хранить — для этого есть отдельные системы вроде Vault (подробнее — в следующем разделе).

03

Пайплайн сборки конфигурации

Для критичных параметров всегда стоит предусматривать значения по умолчанию — будь то тег envDefault у переменных окружения или третий аргумент у флага:

main.gogo
port := flag.Int("port", 8080, "Порт сервера") // имя, дефолт, описание

Собирая всё вместе, получаем предсказуемый пайплайн из шести шагов:

flowchart LR
  A["1. структура
Config"] --> B["2. файл
конфига"] --> C["3. env-
переменные"] --> D["4. флаги"] --> E["5. дефолты
для пропусков"] --> F["6. валидация"]
  F -.->|"провал"| X["приложение падает
как можно раньше"]

Каждый следующий источник может переопределить предыдущий — до финальной проверки

1

Единая структура. Все параметры собираются в одном типе — естественном месте для объединения однородных данных.

2

Файл конфига. Если он указан — это первый источник истины, данные оттуда ложатся в структуру первыми.

3

Env-переменные. Системные настройки, которые логичнее держать вне кода — контейнер или ОС.

4

Флаги. Один-два флага при запуске — тоже нередкий сценарий, не забудь их учесть.

5

Дефолтные значения. Для всего, что критично для работы системы — на случай, если ни один источник не задал значение.

6

Валидация. Порт в допустимом диапазоне, тайм-ауты положительны, URL и пути не пустые (а лучше — соответствуют паттерну). Здесь закладывается безопасность.

// fail fast

Приложение должно падать как можно раньше, если конфигурация некорректна. Упасть с понятной ошибкой лучше, чем незаметно работать неправильно и подводить клиентов.

04

Хранение секретов

Обычные настройки — порт, лог-уровень, размер кеша. А есть секреты — токены, пароли, ключи доступа. Тоже часть конфигурации, но обращаться с ними нужно осторожнее.

  • не хардкодить внутри исходного кода;
  • не класть в git;
  • не писать в лог.
// централизованное хранение

Vault — инструмент для безопасного хранения и выдачи секретов, применяемый только для чувствительных данных, централизованно для всех сервисов компании. Знать о нём стоит, хотя в учебных проектах курса он не понадобится.

Если хочется не собирать всю эту обвязку вручную — библиотека spf13/viper из коробки работает с широким набором форматов и источников конфигурации сразу. На курсе не обязательна, но жизнь облегчает заметно.
