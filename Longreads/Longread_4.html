01

Обобщение кода через дженерики

Дженерики (generics) — способ писать функции и типы, работающие с разными типами данных без потери типобезопасности. Появились в Go 1.18 (март 2022) — сообщество просило о них долго. Проблема, которую они решают, выглядит так:

main.gogo
func MaxInt(a, b int) int {
	if a > b { return a }
	return b
}

func MaxFloat64(a, b float64) float64 {
	if a > b { return a }
	return b
}

func MaxString(a, b string) string {
	if a > b { return a }
	return b
}
// Дублирование кода!
flowchart LR
  A["MaxInt(int, int) int"]
  B["MaxFloat64(float64, float64) float64"]
  C["MaxString(string, string) string"]
  A --> D["Max[T cmp.Ordered](a, b T) T"]
  B --> D
  C --> D

Три одинаковых функции для трёх типов схлопываются в одну обобщённую

main.gogo
// Одна функция для всех сравнимых типов!
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	fmt.Println(Max(10, 20))           // 20
	fmt.Println(Max(3.14, 2.71))       // 3.14
	fmt.Println(Max("hello", "world")) // world
}
[T cmp.Ordered]
обобщённый параметр с наложенным ограничением на тип.
T
имя параметра типа — обычно T, K, V.
cmp.Ordered
само ограничение — какие типы допустимы для T.

Обобщённых параметров у функции может быть и несколько:

main.gogo
func Map[T, U any](slice []T, fn func(T) U) []U {
	result := make([]U, len(slice))
	for i, v := range slice {
		result[i] = fn(v)
	}
	return result
}
// цена дженериков

В коде функция-дженерик — одна запись. Но при компиляции под капотом сгенерируется по копии на каждый реально используемый тип. Итог закономерен: бинарный файл растёт в весе — это стоит держать в голове.

Обобщёнными бывают и структуры — например, пара значений:

main.gogo
type Pair[K, V any] struct {
	Key   K
	Value V
}

func main() {
	p1 := Pair[string, int]{Key: "age", Value: 30}
	p2 := Pair[int, string]{Key: 1, Value: "first"}

	fmt.Println(p1) // {age 30}
	fmt.Println(p2) // {1 first}
}

Отсюда рукой подать до обобщённых кешей, стеков и прочих структур данных.

Ограничения параметров

Тип параметра можно ограничивать вручную. В стандартной библиотеке уже есть готовые ограничения:

ОграничениеЧто разрешает
anyалиас на пустой интерфейс — вообще без ограничений
comparableтолько типы, сравнимые через == и !=
cmp.Orderedтолько упорядоченные типы — с >, <, >=, <=

А ещё ограничения можно писать самому — и, неожиданно, они строятся на интерфейсах:

main.gogo
// Ограничение: тип должен иметь метод String()
type Stringer interface {
	String() string
}

func PrintAll[T Stringer](items []T) {
	for _, item := range items {
		fmt.Println(item.String())
	}
}

Или задать конкретный перечень типов через |:

main.gogo
// Ограничение: только int или float64
type Number interface {
	int | float64
}

func Sum[T Number](numbers []T) T {
	var sum T
	for _, n := range numbers {
		sum += n
	}
	return sum
}

А если нужен и встроенный тип, и любой кастомный тип на его основе — на помощь приходит «приближённое ограничение» ~: конкретный тип и всё, для чего он базовый.

main.gogo
// Разрешает int и пользовательские типы на основе int
type Integer interface {
	~int
}

type MyInt int

func Double[T Integer](value T) T {
	return value * 2
}

func main() {
	var x int = 5
	var y MyInt = 10

	fmt.Println(Double(x)) // 10
	fmt.Println(Double(y)) // 20
}

Сам cmp.Ordered — это как раз такой набор базовых типов (исходник):

cmp.gogo
type Ordered interface {
	~int | ~int8 | ~int16 | ~int32 | ~int64 |
		~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
		~float32 | ~float64 |
		~string
}

Где дженериков пока нет

Методы не могут иметь собственные обобщённые параметры — но могут пользоваться обобщёнными параметрами своего ресивера:

main.gogo
type Container[T any] struct {
	value T
}

// OK: метод использует T из структуры
func (c Container[T]) Get() T {
	return c.value
}

func (c *Container[T]) Set(value T) {
	c.value = value
}

// ОШИБКА: метод не может иметь свои параметры типов
// func (c Container[T]) Convert[U any](fn func(T) U) U {
//     return fn(c.value)
// }
In Go, one of the main roles of methods is to permit types to implement interfaces. It is not clear whether it is reasonably possible to permit parameterized methods to implement interfaces. — из FAQ языка Go

Подробности — в FAQ и в объяснении дизайна. Но «никогда не говори никогда»: на горизонте есть proposal от Роберта Гризмера, одного из отцов-основателей языка, с обоснованием такой возможности — быть может, через год-два политика изменится.

Использование дженериков

Использовать, когда

  • Сложные структуры данных — списки, стеки, деревья, графы
  • Утилитные функции — Map, Filter, Reduce
  • Обобщённые алгоритмы — сортировка, поиск
  • Иначе пришлось бы дублировать код под разные типы

Не использовать, когда

  • Достаточно интерфейса — нужно поведение, а не тип
  • Функция простая и тип заранее известен
  • Начинай с конкретных типов, обобщай позже.
  • Используй понятные имена: T, K, V для простых случаев.
  • Всегда ограничивай типы.
  • Предпочитай интерфейсы, когда нужно поведение.
  • Не злоупотребляй — простота важнее универсальности.
02

Ошибки

Одна из самых холиварных тем в Go — ошибки и их обработка. Исключений в языке нет — есть ошибки, которые рождаются в месте возникновения и поднимаются вверх, до пользователя или до места логирования. В основе — простая концепция errors as values: ошибка не просто условие для проверки, а полноценное значение своего типа, с которым можно работать как с любыми другими данными.

main.gogo
_, err := fmt.Scan(&x)
if err != nil {
	fmt.Println(err)
}
// главное правило

Ошибки нужно обрабатывать всегда. Не пренебрегай этим — вовремя пойманная ошибка это залог успешной работы твоей программы.

Да, шаблонного err != nil в go-коде очень много, и это то, что пугает новичков. Сообщество не раз предлагало от него избавиться: пример 1, пример 2, пример 3. Но команда языка выпустила отдельный пост, где прямо заявила: мнение не изменится, err != nil — лучший подход для Go. С этим можно смириться и идти дальше.

Что такое ошибка в Go? Значение. И ещё — интерфейс:

builtin.gogo
type error interface {
	Error() string
}

Значит, ошибкой может быть любой тип, реализующий этот интерфейс — error в Go по сути встроенный тип, с которым можно работать по-разному.

Контекст ошибки

Плохой пример: ошибка поднимается наверх без единой зацепки о том, что случилось:

main.gogo
func two() error {
	err := one()
	if err != nil {
		return err // Поднимаем ошибку наверх, не понимая контекста
	}
	return nil
}

func three() error {
	err := two()
	if err != nil {
		return err // И снова — контекст потерян
	}
	return nil
}

Ошибку стоит обогащать: параметрами функции, значениями переменных, дополнительным сообщением. Проще всего — через fmt.Errorf и глагол %w, который сохраняет доступ к исходной ошибке:

main.gogo
return fmt.Errorf("ошибка при обработке данных пользователя %s: %w", userID, err)

Тот же результат даёт метод Wrap из сторонних пакетов вроде github.com/cockroachdb/errors.

уровня 1"]

Каждый %w добавляет звено в цепочку — errors.Is/errors.As проходят её насквозь

ИнструментЧто делает
errors.Newсоздаёт новую, «исходную» ошибку
fmt.Errorf + %wоборачивает существующую ошибку контекстом, сохраняя цепочку
errors.Isищет в цепочке конкретную ошибку (в т.ч. sentinel)
errors.Asищет в цепочке ошибку конкретного типа и извлекает её
errors.Unwrapдостаёт из обёртки следующую ошибку в цепочке

Создать «исходную» ошибку просто:

main.gogo
var ErrInvalidArgument = errors.New("invalid argument")

func checkArgument(a int) error {
	if a == 0 {
		return ErrInvalidArgument
	}
	return nil
}
// соглашение

Sentinel-ошибки по конвенции называют с префиксом Err... (для экспортируемых) или err... (для приватных).

А проверить, что за ошибка пришла и какого она типа — errors.As:

main.gogo
type MyError struct {
	Code int
	Msg  string
}

func (e *MyError) Error() string {
	return fmt.Sprintf("Ошибка %d: %s", e.Code, e.Msg)
}

func doSomething() error {
	return fmt.Errorf("дело дрянь: %w", &MyError{Code: 500, Msg: "Сервер недоступен"})
}

func main() {
	var targetErr *MyError

	err := doSomething()
	if errors.As(err, &targetErr) {
		fmt.Println("Код ошибки:", targetErr.Code, "Сообщение:", targetErr.Msg)
	} else {
		fmt.Println("Произошла неизвестная ошибка")
	}
}

В версии 1.26 синтаксис упростили:

main.gogo
pathError, ok := errors.AsType[*fs.PathError](err)

Как избавиться от err != nil

Способ есть, но используется он редко — идиоматичным его не назвать. Можно абстрагировать обработку ошибок в отдельный объект:

main.gogo
type errorHandler struct {
	SampleObject sampleObjectType
	Err          error
}

func (handler *errorHandler) Write(param ParamType) {
	if handler.Err != nil {
		return
	}
	_, handler.Err = handler.SampleObject.SomeAction(param)
}
03

Отложенные вызовы: defer, panic, recover

Ключевое слово defer откладывает выполнение функции до завершения той функции, в чьём теле оно вызвано — удобно, например, писать закрытие соединения сразу рядом с его открытием.

В теле функции можно вызвать сколько угодно defer — выполняются они по принципу LIFO: последним объявлен — первым выполнен.

main.gogo
func Example() {
	for i := 3; i > 0; i-- {
		defer fmt.Print(i, " ") // Выведет в обратном порядке: 1 2 3
	}
}

func Example3() {
	for i := 3; i > 0; i-- {
		defer func(n int) { // Анонимная функция тоже подходит
			fmt.Print(n, " ")
		}(i)
	}
}
flowchart TB
  P1["defer Print(3) — объявлен первым"] --> P2["defer Print(2)"] --> P3["defer Print(1) — объявлен последним"]
  P3 -.->|"выполнится первым"| R1["Print: 1"]
  P2 -.->|"затем"| R2["Print: 2"]
  P1 -.->|"выполнится последним"| R3["Print: 3"]

LIFO: последний объявленный defer отрабатывает первым

defer гарантирует выполнение своего блока кода вне зависимости от того, случилась ли по пути ошибка.

Паники не ошибки

Аналог необрабатываемых исключений в Go — паника, вызываемая через panic(). Это фатальный сбой, после которого дальнейшее выполнение программы бессмысленно: приложение падает, печатая в стандартный вывод стек вызовов с местом паники.

main.gogo
func foo() {
	panic("Something went wrong!")
}

func main() {
	fmt.Println("Start")
	foo()
	fmt.Println("End") // Эта строка не выполнится
}
// dont panic

Соблазн раскидать panic повсюду велик — но принцип языка прямо против: паника нужна лишь в крайних случаях. Это не аналог исключений из других языков, а сигнал «дальше действительно нельзя».

Паника уместна

  • Ошибка фатальна, продолжать работу невозможно
  • Ошибка ломает логику программы и не может быть исправлена на месте
  • Ошибку в принципе невозможно обработать

Паника не нужна

  • Почти всегда — когда ошибка ожидаема и некритична
  • Когда её можно исправить, залогировать или передать дальше
  • Когда программа способна продолжить работу

Ловец паник

Паника крашит выполнение — но её можно перехватить, обработать и продолжить работу как ни в чём не бывало. Для этого есть встроенная функция recover(). Даже после паники управление переходит в ближайший defer — вот он и может позвать recover.

// как работает recover

recover() действует только внутри defer. Вызванная где-то ещё во время активной паники — она просто пропускает панику дальше и программа всё равно завершится; а без активной паники — вернёт nil, и работа продолжится штатно.

recover() работает только внутри defer — это единственная точка входа для перехвата паники

main.gogo
func Example() {
	fmt.Println("Inside function")
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("Recovered:", r)
		}
	}()
	panic("Panic!")
}

func main() {
	Example()
	fmt.Println("Main function continues")
}
выводstdout
Inside function
Recovered: Panic!
Main function continues

Как и самой паники, восстановления после неё стоит избегать в обычном коде — оставь его для действительно крайних случаев. Dont panic!
