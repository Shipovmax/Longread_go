01

Конкурентность vs параллелизм

В Python конкурентность держится на asyncio, threading и multiprocessing — модулях в обход ограничений языка. В Rust — на прямом создании тредов ОС и сторонних рантаймах вроде Tokio. В Go конкурентная работа реализована прямо под капотом языка — и это выгодно его выделяет.

Параллелизм — несколько задач выполняются буквально одновременно, на разных ядрах, не деля между собой ресурсы одного ядра. Как если бы амбидекстер рисовал картину сразу двумя руками.

Конкурентность — псевдопараллельность: задачи выполняются на одном ядре, которое постоянно переключается между ними, создавая иллюзию одновременности. Как если бы художник без амбидекстрии постоянно перекладывал кисть из руки в руку, работая то одним, то другим оттенком.

Конкурентность реализуема и на одном ядре, и на нескольких; параллелизм без нескольких ядер невозможен. Параллелизм — свойство системы; конкурентность — свойство языка.

быстрее отвечать на запросы эффективнее использовать ресурсы отзывчивый интерфейс много задач одновременно

Всё это Go даёт из коробки — просто, безопасно, благодаря одной изящной абстракции: горутинам.

02

Горутины — единицы конкурентности вместо потоков

Операционные системы выполняют программы через треды/потоки — но в Go это не единица выполнения. Причина в трёх практических минусах тредов ОС:

  • стек треда имеет фиксированный размер (до ~8 МБ) без возможности расти или сжиматься;
  • создание треда — дорогая операция, и много тредов ОС создать физически не может (счёт на тысячи);
  • переключение треда дорого: нужно сохранить состояние текущего, снять с ядра, загрузить состояние нового и запустить.

Поэтому Go спустился на уровень ниже и создал собственные потоки внутри языка — горутины. В исходном коде это структура; по сути — единица выполнения конкурентной работы в языке.

ХарактеристикаТред ОСГорутина
Стекфиксирован, до ~8 МБот 2 КБ, растёт до 1 ГБ (и сжимается обратно)
Созданиедорого, счёт на тысячидёшево, счёт на миллионы
Переключениедорого, силами ОСдёшево, силами языка
1000 задач≈ 8 ГБ памяти≈ 2 МБ памяти в начальном состоянии

Планировщик ОС, распределяющий потоки по ядрам, ощутимо медленнее встроенного планировщика Go. Дополнительная абстракция работает не в kernel-space, а в user-space — и именно на этом Go выигрывает скорость.

В коде горутина — это функция или метод, выполняющиеся условно «параллельно» остальным. У любой программы уже есть одна горутина при старте — это main(), выполняющаяся строго последовательно. Как заставить Go создавать больше?

Как работать с горутинами

Горутина создаётся ключевым словом go перед вызовом функции — она начинает выполняться независимо и конкурентно с остальными:

main.gogo
func sayHello(name string) {
	fmt.Printf("Привет, %s!\n", name)
}

func main() {
	fmt.Println("Начинаем программу...")

	go sayHello("Анна")  // Запускаем первую горутину
	go sayHello("Борис") // Запускаем вторую горутину

	fmt.Println("Программа завершена")
}
выводstdout
Начинаем программу...
Программа завершена
// неожиданно?

go лишь ставит горутину в очередь на выполнение — не гарантирует, что она успеет отработать до завершения main. Добавь time.Sleep() перед последним Println — и увидишь оба приветствия. Спецификация языка не гарантирует порядок выполнения горутин.

Горутины работают и с анонимными функциями — заодно являясь замыканиями, захватывающими переменные из своей области видимости:

main.gogo
go func() {
	fmt.Println("Анна")
}() // Не забываем () в конце — иначе функция не готова к запуску

go sayHello("Борис")

Горутину даёт функция (анонимная или обычная) или метод, выполняются они в непредсказуемом порядке. А управляет всем этим — планировщик.

03

Планировщик и модель GMP

Планировщик (scheduler, «шедулер») — механизм, управляющий очерёдностью, временем и ресурсами для выполнения задач. Полагаться на планировщик ОС Go не мог по двум причинам: язык кросс-компилируемый и не может привязываться к конкретной ОС, а планировщик ОС попросту не знает о существовании горутин — только о потоках, и заточен под совсем другую задачу: распределение времени ЦПУ между разными программами системы.

Раз в языке появилась своя абстракция — управлять ей должен планировщик самого языка. Автор планировщика Go — наш соотечественник, Дмитрий Вьюков.

// принцип M : N

Произвольное количество горутин (M) выполняется на произвольном количестве потоков ОС (N). Планировщик Go не управляет самими потоками напрямую — он не знает, когда поток реально исполняется на ядре, но пока тот на ядре, успевает прогнать через него несколько горутин конкурентно.

Модель называется GMP — goroutine, processor, machine:

G — Goroutine
сама горутина: стек, состояние выполнения (регистры, счётчик), статус (пауза, выполнение, готовность).
P — Processor
виртуальный процессор — якорь для горутин; количество P не превышает числа физических ядер (но может быть меньше). У каждого P своя локальная очередь горутин, до 256 штук: они попадают туда из глобальной очереди, у соседних P (через work stealing) или рождаются прямо в текущей выполняемой горутине.
M — Machine
абстракция треда ОС. Именно M выполняет горутины, прикрепляясь к конкретному P. При тяжёлой блокирующей операции (например, сетевой вызов) M открепляется от P и продолжает жить с потоком ОС, а планировщик просит у ОС новый M для освободившегося P.

Ещё есть GRQ — глобальная очередь горутин, не попавших ни в один P. Каждый P периодически туда заглядывает, чтобы забрать себе пачку работы.

Основные механизмы планировщика

1

Work stealing. Когда локальная очередь P опустела, он лезет к случайному соседнему P и, если там есть свободные G, крадёт себе половину — так работа P не прерывается впустую.

2

Sysmon. Отдельная горутина, стартующая вместе с планировщиком. Периодически проверяет заблокированные M, запускает сборщик мусора и вытесняет горутины, которые слишком долго не отдают управление.

3

Network Poller. Ещё одна отдельная горутина — опрашивает сетевые соединения через epoll/kqueue/IOCP и возвращает горутины в готовность, как только соединение готово.

Параллелизм через GOMAXPROCS

Переменная GOMAXPROCS задаёт максимальное число P для программы — тем самым определяя, сколько ядер ей реально доступно:

main.gogo
func main() {
	// Только одно ядро — чистый конкурентный код
	runtime.GOMAXPROCS(1)

	// Все доступные ядра (по умолчанию, начиная с Go 1.5).
	// Если ядер больше двух, код и конкурентный, и параллельный одновременно
	runtime.GOMAXPROCS(runtime.NumCPU())
}
04

Каналы между горутинами

Как синхронизировать горутины между собой? Через каналы — потокобезопасный тип, ключевой инструмент конкурентного Go. Каналы реализуют message passing: горутины не лезут напрямую в общие данные (memory sharing), а координируются, передавая сообщения по каналу в порядке FIFO. Под капотом канал — тоже структура (исходник), тут без сюрпризов.

Канал объявляется через make — буферизированным или небуферизированным (число после запятой в типе):

main.gogo
ch := make(chan int)     // Небуферизированный
buf := make(chan int, 3) // Буферизированный на 3 элемента

Небуферизированный канал синхронный: отправитель блокируется, пока получатель не будет готов принять (и наоборот). Буферизированный — асинхронный до заполнения буфера: внутри кольцевой буфер на N элементов, и обе стороны не блокируются, пока в нём есть место.

sequenceDiagram
  participant G1 as Горутина 1 (отправитель)
  participant CH as ch (небуферизированный)
  participant G2 as Горутина 2 (получатель)
  G1->>CH: ch <- 42
  Note over G1,CH: заблокирована — ждёт получателя
  G2->>CH: value := <-ch
  CH-->>G1: разблокирована
  CH-->>G2: получено 42

Небуферизированный канал — это рукопожатие: обе стороны ждут друг друга

1
2
3
4

Буфер на 3 занят целиком — четвёртая отправка блокируется, пока кто-то не прочитает

Чёткого правила «когда буфер, когда нет» не существует — обычно стоит начать с небуферизированного канала, и добавлять буфер только если блокировки заметно тормозят код. Оператор <- и читает, и пишет в канал, в зависимости от позиции.

Работа с каналами

main.gogo
// Чтение из канала в цикле
for {
	val, ok := <-ch // Второй параметр — признак закрытия канала
	if !ok {
		break
	}
	fmt.Println(val)
}

// Запись в канал в цикле
for range n {
	ch <- n
}
close(ch) // Закрываем канал после записи
// важное правило

Канал закрывает та горутина, которая в него пишет — только она понимает, когда его жизненный цикл завершён. Заводя канал, сразу планируй, где и когда закроешь его.

Не проверяя закрытие, читающая горутина продолжит получать zero value типа канала бесконечно. Исключение — for range по каналу: он сам следит за закрытием и завершает цикл:

main.gogo
for val := range ch {
	fmt.Println(val)
}
// осторожно

Из закрытого канала читать можно. А вот запись в закрытый канал, как и его повторное закрытие, — гарантированная паника. Для закрытия удобно использовать defer.

Каналы бывают направленными — только на запись или только на чтение. Это безопасность на этапе компиляции, чёткость контракта функции и более читаемый код. Из двунаправленного в направленный конвертировать можно, обратно — нет:

main.gogo
var bidirectional chan int = make(chan int)
var sendOnly chan<- int = bidirectional    // OK
var receiveOnly <-chan int = bidirectional // OK
// var bidir2 chan int = sendOnly          // Ошибка компиляции

func producer(dataChan chan<- string) {} // Только отправка

Мультиплексирование каналов

Когда каналов несколько, за ними следит конструкция select case — как switch, но только для каналов, и умеет ждать сразу несколько операций одновременно. В отличие от switch, кейсы select проверяются не по порядку, а рандомно, а default срабатывает, если ни один канал не готов прямо сейчас:

main.gogo
for {
	select {
	case msg1 := <-ch1:
		fmt.Printf("Получено из канала 1: %s\n", msg1)
	case msg2 := <-ch2:
		fmt.Printf("Получено из канала 2: %d\n", msg2)
	case <-timeout:
		fmt.Println("Таймаут!")
		return
	default:
		fmt.Println("Ни один канал не готов, делаем другую работу...")
		time.Sleep(1 * time.Second)
	}
}

nil-каналы и deadlock

nil-канал — объявленный, но не инициализированный: все операции с ним блокируются навсегда, а закрытие — паника. Пригождается это неожиданно часто: превратив рабочий канал в nil, можно заставить select временно игнорировать его case, динамически включая и выключая каналы.

// deadlock

Deadlock — все горутины программы ждут событий, которые никогда не случатся. Рантайм Go умеет это ловить сам и падает с fatal error: all goroutines are asleep - deadlock!

main.gogo
func channelDeadlock() {
	ch := make(chan int)

	ch <- 42 // Нет получателя — заблокирует навсегда

	fmt.Println("Эта строка никогда не выполнится")
}
// мантра Go

«Не общайтесь через общую память — делитесь памятью через общение». Каналы почти всегда предпочтительнее остальных механизмов синхронизации.

05

Гонки данных и гонки состояний

Race condition — гонка состояний: результат зависит от непредсказуемого порядка выполнения горутин при одновременном доступе к общим данным. Частный, более узкий случай — data race: несколько горутин одновременно обращаются к памяти, и хотя бы одна из них пишет. Консистентность данных при этом нарушается.

Мапы в Go конкурентно небезопасны намеренно жёстко: при одновременном доступе программа сама впадает в панику, чтобы проблему нельзя было не заметить. А вот обычный data race так себя не выдаёт:

main.gogo
// Небезопасный инкремент
func simpleRaceCondition() {
	counter := 0

	go func() { counter = 1 }()
	go func() { counter = 100 }()

	time.Sleep(1 * time.Second)

	fmt.Printf("Результат: %d\n", counter)
	// Результат непредсказуем: 1 или 100
}
непредсказуемые результаты повреждение данных паника сложная отладка

Отслеживание гонок

Go даёт встроенный детектор гонок — достаточно одного флага:

терминалbash
# Запуск программы с детектором
go run -race main.go

# Запуск тестов с детектором
go test -race ./...

# Сборка с детектором
go build -race main.go
