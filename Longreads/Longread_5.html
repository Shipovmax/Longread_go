01

Пакеты, модули и области видимости

По мере роста кодовой базы неизбежно встают вопросы: как организовать код, чтобы он оставался понятным? Как обеспечить переиспользование? Как совместить гибкость с типобезопасностью? Go отвечает на них двумя механизмами: пакетами — организация кода и область видимости, и модулями — версии, зависимости, границы проекта.

Пакет — набор файлов с одинаковым объявлением package в одном каталоге, компилируемых как единое целое: основная единица организации и переиспользования кода. Модуль — коллекция пакетов, публикуемая и версионируемая как единое целое; определяется файлом go.mod в корне и на практике почти всегда — отдельная программа или сервис.

дерево каталоговмодуль
example.com/my-module # модуль, представляющий собой программу
├── go.mod
├── cmd/        # пакет с точкой входа в программу
│   └── app/
│       └── main.go # точка входа в программу
├── internal/   # пакеты, доступные только внутри этого модуля/программы
│   ├── config/ # пакет для работы с конфигурациями
│   └── server/ # пакет для работы с серверной логикой
└── pkg/        # общедоступные пакеты для прочих программ и сервисов
    ├── database/
    └── logger/

Точки входа — в cmd, внутренние компоненты — в internal, публичные пакеты — в pkg. Такое деление держит границы между компонентами чистыми.

Работа с пакетами

Каждый файл начинается с объявления пакета — package clause:

config.gogo
package config

В одном пакете может быть сколько угодно файлов. Особый случай — пакет main: точка входа исполняемой программы, содержащая функцию main.

main.gogo
package main

func main() {
	// Начало выполнения программы
}
// правило имени

Директорию и пакет внутри неё принято называть одинаково. Технически можно назвать директорию config, а внутри объявить package configuration — но это дурной тон. А вот два разных package clause в одной директории компилятор просто не примет — это запрещено языком.

Код одного пакета подключается к другому через import:

main.gogo
import (
	"fmt"                        // стандартный пакет
	"my-module/internal/config"  // внутренний пакет
	"github.com/sirupsen/logrus" // внешний пакет
)

func main() {
	cfg, err := config.Load()
	if err != nil {
		logrus.WithError(err).Fatalln("loading config")
	}
	fmt.Printf("Config loaded: %+v\n", cfg)
}

Для стандартной библиотеки достаточно имени пакета (net/http). Для своего пакета нужен полный путь пакета — обычно путь модуля плюс подкаталог (my-module/internal/config). Путь может быть абсолютным (golang.org/x/net/html) или указывать на пакет стандартной библиотеки. Для внешних зависимостей используется go get — о нём чуть ниже.

flowchart LR
  A["пакет A"] -->|imports| B["пакет B"]
  B -.->|imports| A

import cycle not allowed — Go запрещает циклические импорты ради предсказуемой сборки

Это нужно для быстрой компиляции, предсказуемой иерархии зависимостей и защиты от архитектурного беспорядка — при циклах порядок сборки было бы невозможно (или почти невозможно) определить.

2

Области видимости пакетов

Видимость идентификатора внутри пакета, как и раньше, определяется регистром первой буквы: экспортируемые начинаются с заглавной, неэкспортируемые — с маленькой.

user.gogo
package user

// Экспортированный тип (виден извне)
type User struct {
	Name string // экспортированное поле
	age  int    // неэкспортированное поле
}

// Экспортированная функция
func NewUser(name string, age int) User {
	return User{Name: name, age: age}
}

// Неэкспортированная функция
func validate(u User) bool {
	return u.Name != "" && u.age > 0
}

NewUser — контролируемый конструктор, гарантирующий валидность данных; age и validate скрыты от внешнего мира:

main.gogo
u := user.NewUser("Alice", 30)

fmt.Println(u.Name) // доступно

fmt.Println(u.age)  // ошибка компиляции
user.validate(u)    // ошибка компиляции

Функция init

Каждый пакет может содержать init — выполняется на стадии инициализации:

database.gogo
package database

import "log"

var db *Database

func init() {
	// Выполнится один раз при импорте пакета
	log.Println("Initializing database...")
	db = &Database{}
}

type Database struct {
	// ...
}

init запускается, если пакет вошёл в сборку — то есть был импортирован в main напрямую или через цепочку импортов. Часто используется для настройки глобальных переменных или регистрации драйверов — но для сложной инициализации с возможными ошибками лучше явные конструкторы.

Особенности init

  • В одном пакете может быть несколько функций init
  • Выполняются после инициализации глобальных переменных
  • Порядок: сначала импортируемые пакеты, затем текущий
  • Не принимают параметров и ничего не возвращают

Чем это опасно

  • Порядок срабатывания при взаимных импортах легко упустить — получаешь необъяснимое поведение
  • Такие функции тяжело тестировать по своей природе
  • Часто используются для глобального состояния — а это плохой тон
  • Ничего не возвращают — ошибки внутри чаще всего просто паникуют

Именование пакетов

Стоит избегать «статтеринга» (stuttering) — повторения имени пакета в именах его экспортируемых идентификаторов. Плохо:

user.gogo
package user

func UserCreate() { /* ... */ }
func UserDelete() { /* ... */ }
// снаружи: user.UserCreate() — избыточно

Лучше:

user.gogo
package user

func Create() { /* ... */ }
func Delete() { /* ... */ }
// снаружи: user.Create() — читается как строка в книге

Стоит избегать и обобщённых названий вроде common, helpers, utils — по такому имени невозможно понять зону ответственности пакета. Имя должно быть коротким и содержательным: pricing, database. Ориентир — исходный код самого Go.

Модули

Каждый Go-проект начинается с одной команды:

терминалbash
# Создание нового модуля
go mod init github.com/username/project-name

Появляются два файла: go.mod — описание модуля и зависимостей, go.sum — криптографические хеши зависимостей.

go.modgo
module github.com/username/project-name

go 1.25

require (
	github.com/gin-gonic/gin v1.9.1
	github.com/golang-migrate/migrate/v4 v4.16.2
	github.com/lib/pq v1.10.9
	github.com/spf13/viper v1.16.0
	gorm.io/driver/postgres v1.5.2
	gorm.io/gorm v1.25.4
)

require (
	github.com/bytedance/sonic v1.9.1 // indirect
	github.com/chenzhuoyu/base64x v0.0.0-20221115062448-fe3a3abad311 // indirect
	// ... другие косвенные зависимости
)
module
уникальное имя проекта в экосистеме Go. При доменном имени (github.com/..., gitlab.com/...) Go ожидает найти по этому пути действующий git-репозиторий и умеет качать зависимости прямо из него. Для непубликуемых проектов подойдёт и простое имя без домена, но домен лучше указывать заранее — ради совместимости на будущее. Смена имени модуля потребует правки всех импортов в проекте.
go
минимальная версия Go, нужная для сборки — гарантирует совместимость с используемыми возможностями языка и не даёт собрать проект на устаревшем компиляторе.
require
список зависимостей: прямых (импортируются в коде проекта напрямую) и косвенных (нужны прямым зависимостям, помечены // indirect) — пометка помогает понять дерево зависимостей и безопасно чистить лишнее.
replace
подменяет зависимость на другую версию или локальный путь — пригодится, когда отлаживаешь баг в форке чужой библиотеки или тестируешь исправление до официального патча: replace github.com/old/package => ../local/package.
exclude
запрещает загрузку конкретной версии зависимости — например, той, где найдена уязвимость: exclude github.com/problematic/package v1.5.0.

Модуль резолвится по доменному имени в несколько шагов:

1

Go определяет хостинг-платформу по домену (github.com, gitlab.com и т. д.).

2

Обращается к API платформы за информацией о репозитории.

3

Скачивает нужную версию или коммит.

4

Кэширует зависимость локально.

// зачем go.sum

Представь заказ из интернет-магазина: go.sum — это чек с уникальными номерами каждого товара. Курьер привёз посылку — ты сверяешь номера с чеком. Если кто-то подменил товар, это сразу видно.

1

Надёжная защита. При сборке Go сверяет скачанные пакеты с хешами в go.sum — подмену на вредоносный код он остановит немедленно.

2

Идеальная воспроизводимость. Все в команде и весь CI/CD получают ровно те же версии зависимостей.

3

Полная история версий. Хешятся и прямые, и косвенные зависимости, вплоть до конкретных коммитов.

Файл обновляется автоматически — при go get, обновлении зависимостей и go mod tidy. Редактировать руками не нужно, а вот исключать из git — нельзя: это твоя страховка.

Работа с зависимостями

КомандаЧто делает
go get pkgдобавляет последнюю версию зависимости
go get pkg@v1.9.1добавляет конкретную версию — предпочтительнее @latest
go get -u ./...обновляет все зависимости проекта
go mod tidyсортирует, обновляет и убирает неиспользуемые зависимости
go install pkg@versionсобирает и ставит бинарь в $GOBIN, не трогая go.mod проекта

Последняя команда — типичный способ поставить внешние dev-инструменты (линтеры, генераторы, форматтеры), не засоряя зависимости самого проекта:

терминалbash
go install golang.org/x/tools/cmd/goimports@latest
go install github.com/golangci/golangci-lint/cmd/golangci-lint@v1.55.2
// не забывай

Периодически вызывай go mod tidy — он держит go.mod в чистоте.

Важная информация о базовых пакетах

Go даёт особый механизм ограничения доступа: любой пакет внутри директории internal доступен только пакетам своего модуля.

дерево каталоговмодуль
my-module/
├── internal/
│   └── database/  // доступен только внутри my-module
├── api/
│   └── handler.go // может импортировать my-module/internal/database
└── client/
    └── main.go    // может импортировать my-module/internal/database
flowchart LR
  A["api/handler.go
тот же модуль"] -->|разрешено| I["internal/database"]
  B["client/main.go
тот же модуль"] -->|разрешено| I
  C["другой модуль,
импортирующий my-module"] -.->|запрещено| I

internal доступен только коду внутри собственного модуля — снаружи он попросту невидим

internal можно объявить не только в корне модуля, а на любом уровне вложенности — тогда правило сужается до родительского пакета и его подпакетов:

дерево каталоговмодуль
my-module/
├── internal/
│   └── database/           // доступен только внутри my-module
│       ├── internal/
│       │   └── anypackage/ // доступен только внутри my-module/internal/database
│       └── postgres/       // может импортировать .../database/internal/...
├── api/
│   └── handler.go // может импортировать database, но не database/internal/...
└── client/
    └── main.go    // может импортировать database, но не database/internal/...

А если пакетом всё же нужно поделиться с миром — для этого pkg:

дерево каталоговмодуль
my-module/
├── internal/
│   └── database/       // доступен только внутри my-module
├── pkg/
│   └── csv_converter/  // доступен и внутри my-module, и снаружи
├── api/
│   └── handler.go
└── client/
    └── main.go
// осторожно с pkg

pkg/ легко превращается в «свалку общих утилит», а у зависящих модулей начинаются проблемы с версионированием и жёсткой привязкой к чужому сервису. Используй его как можно реже — а если подпакетом начинают пользоваться сразу несколько сервисов, выноси его в отдельную библиотеку.

02

Структура проекта на Go

Правильная организация проекта снижает когнитивную нагрузку, ускоряет ревью и упрощает онбординг. Ключевая мысль про Go: у него нет «единственно правильной» структуры (layout). Важно, чтобы команда договорилась о наборе паттернов заранее — и последовательно им следовала, не боясь эволюционировать структуру по мере роста проекта. В open-source такие соглашения часто фиксируют в CONTRIBUTING.md.

Basic command

Официальный гайдлайн «Organizing a Go module» — не строгий стандарт, а рекомендации авторов языка. Самый простой паттерн — Basic command: минимальная исполняемая программа, весь код в пакете main в корне.

дерево каталоговlayout
project-root-directory/
  go.mod
  auth.go
  auth_test.go
  client.go
  main.go

Точку входа по конвенции держат в main.go. Подходит для небольших программ, которым не нужно деление логики по пакетам.

Server project

Server project — паттерн для серверов: логика прячется под internal, все точки входа собираются в cmd — это удобно, когда в репозитории много не-Go кода рядом.

дерево каталоговlayout
project-root-directory/
  go.mod
  internal/
    auth/
      ...
    metrics/
      ...
    model/
      ...
  cmd/
    api-server/
      main.go
    metrics-analyzer/
      main.go
    ...
  ... остальные директории проекта с не-Go кодом
  • Сразу видно, что экспортируемых Go-пакетов нет — весь код живёт в internal/ и cmd/;
  • Точки входа явно собраны в отдельной cmd/;
  • Остальные директории (docker/, chart/, .gitlab/) не мешают Go-коду — их можно добавлять как угодно.

Большинство других layout'ов на практике — это Server project плюс несколько добавленных директорий под свои нужды.

Другие ориентиры

1

golang-standards/project-layout — неофициальный, но широко используемый набор рекомендаций для крупных проектов. Стандартом он не является: Расс Кокс официально подтвердил, что у Go в принципе нет стандартов такого рода.

2

Исходный код Go — хороший ориентир по именованию и структуре пакетов, хоть местами и противоречит собственным идиомам языка. В любом правиле бывают исключения.

3

Более общие архитектурные подходы стоит знать хотя бы поверхностно — они пригодятся не только в Go.
