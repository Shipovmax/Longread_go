01

HTTP-протокол

Как только сервис выходит за границы своего процесса, начинается сетевое взаимодействие — а для него нужен протокол: набор правил и договорённостей о формате запросов и ответов. Здесь мы всегда имеем дело с клиент-серверной архитектурой: клиент отправляет запрос, желая получить или изменить данные, сервер его принимает, обрабатывает и отвечает. Практически любой сервис бывает и клиентом, и сервером одновременно — а правила их общения в нашем случае задаёт HTTP.

sequenceDiagram
  participant C as Клиент
  participant S as Сервер
  C->>S: HTTP-запрос (метод, URI, заголовки, тело)
  Note over S: обработка
  S-->>C: HTTP-ответ (код, заголовки, тело)

Базовый цикл — клиент инициирует, сервер отвечает; протокол сам по себе не помнит, что было раньше

HTTP (HyperText Transfer Protocol) относится к прикладному уровню и в OSI, и в TCP/IP — то есть отвечает именно за передачу данных в сети. Обе модели полезно понимать в будущем, но здесь это не главное.

передача страниц и файлов обработка форм сессии и авторизация JSON / XML / бинарные данные
// протокол без памяти

Каждый запрос независим от остальных — сервер не помнит прошлые запросы клиента. Cookie и данные сессии позволяют сымитировать состояние, но живут они, как правило, только в рамках одного соединения.

Сообщения передаются простым текстом в ASCII/UTF-8 и называются «запрос» и «ответ».

HTTP-запрос

запросhttp
POST /api/users/123 HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: application/json
Authorization: Bearer abc123

{"key": 123}
стартовая строка
метод, эндпоинт (точнее — URI, компактная строка-идентификатор ресурса) и версия протокола.
заголовки
метаданные запроса в виде ключ-значение — техническая информация, задающая контекст.
тело запроса
данные для POST/PUT; у GET тела по конвенции не бывает вовсе.
МетодЧто означаетИдемпотентен
GETполучить данные/ресурсда
POSTсоздать данные на серверенет
PUTобновить/заменить ресурсда
DELETEудалить ресурсда

Идемпотентность — повторное выполнение операции даёт тот же результат, что и однократное. Из четырёх методов только GET ничего не меняет по своей природе — остальные так или иначе трогают состояние (полный список методов заметно шире).

path-параметр
обязательная часть пути: в /api/users/{userID} число 123 — идентификатор конкретного ресурса.
query-параметр
необязательный, после ?: /api/users/{userID}?offset=20&limit=2, разделяются &. Отсутствие параметра нужно обрабатывать через значения по умолчанию.

Заголовки запроса — контекст в чистом виде:

ЗаголовокНазначение
Authorization / Cookieаутентификация и определение пользователя
Hostк какому ресурсу идёт обращение
Acceptожидаемый тип и кодировка содержимого
User-Agent / Accept-Languageбраузер, ОС, язык клиента

Полный список — в справочнике MDN.

HTTP-ответ

ответhttp
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 1234
Date: Mon, 23 Oct 2023 12:00:00 GMT
Server: nginx/1.18.0

{
  "id": 123,
  "name": "John Doe",
  "email": "john@example.com"
}

Стартовая строка теперь несёт версию протокола, код и статус ответа — например, 404 Not Found или 500 Internal Error. Заголовки и тело выполняют ту же роль, что и в запросе.

02

REST

Контракт общения клиента и сервера логично держать на стороне сервера — клиентов может быть множество, и именно сервер несёт ответственность за удобное API. REST — не протокол, а архитектурный стиль: набор принципов для построения веб-систем. Путать REST с протоколом — классическая ошибка на собеседованиях.

1

Клиент-серверная архитектура. Разделение обязанностей: клиент — потребление API, сервер — данные и эндпоинты, развиваются независимо.

2

Отсутствие состояния (stateless). Сервер не хранит сессию клиента — каждый запрос самодостаточен.

3

Кеширование. Ответ явно помечен как кешируемый или нет — чтобы клиент мог переиспользовать данные.

4

Единообразие интерфейса. Один унифицированный способ общения — через HTTP-методы, понятие ресурса и URL.

5

Многослойная система. Балансировщик, обработчик и другие уровни не видят дальше соседнего.

6

Код по требованию (необязательно). Сервер может отдать клиенту исполняемый код — например, скрипт.

Первые пять пунктов выполнены — систему можно называть соответствующей REST, или RESTful.

REST API реализует четыре операции CRUD (create, read, update, delete) ровно через уже знакомые методы: GET читает, POST создаёт, PUT обновляет/заменяет, DELETE удаляет.

Всё в REST вращается вокруг ресурса — любой сущности с уникальным идентификатором-URI: документ, товар, пользователь. Клиент работает не с самим ресурсом напрямую, а с его представлением — JSON, XML, бинарные данные. /users/123 отдаёт один ресурс, /users — массив ресурсов.

хорошо: ресурсно-ориентированные URI
GET    /api/users          # все пользователи
GET    /api/users/123      # пользователь 123
POST   /api/users          # создать пользователя
PUT    /api/users/123      # обновить пользователя 123
DELETE /api/users/123      # удалить пользователя 123
GET    /api/users/123/orders  # заказы пользователя 123
плохо: глаголы в URI
GET    /api/getUsers        # неправильно!
POST   /api/createUser      # неправильно!
PUT    /api/updateUser/123  # неправильно!

REST — не строгий стандарт, а философия. Но в индустрии ей принято следовать.

03

HTTP-серверы в Go

Всё нужное для сервера уже есть под капотом языка — пакет net/http. Минимальный сервер укладывается в десяток строк:

main.gogo
func weatherHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "Добро пожаловать в сервис погоды!")
}

func main() {
	http.HandleFunc("/weather", weatherHandler)
	fmt.Println("Сервер запущен на порту 8080...")

	if err := http.ListenAndServe(":8080", nil); err != nil {
		fmt.Println("Ошибка запуска сервера:", err)
	}
}

Обработчик (handler) — объект с методом ServeHTTP(w http.ResponseWriter, r *http.Request), вызываемым на каждый входящий запрос. http.HandleFunc сам оборачивает обычную функцию в этот интерфейс. nil вторым аргументом ListenAndServe означает «взять глобальный http.DefaultServeMux» — маршрутизатор по умолчанию, в который мы и зарегистрировали обработчик.

http.ResponseWriter
интерфейс для отправки ответа — через него пишутся данные и заголовки.
*http.Request
вся информация о запросе: URL, метод, тело.

Когда нужен контроль над параметрами сервера — создаём его сами:

main.gogo
func handler(w http.ResponseWriter, r *http.Request) {
	switch r.URL.Path {
	case "/":
		fmt.Fprintln(w, "главная")
	case "/about":
		fmt.Fprintln(w, "о проекте")
	default:
		http.NotFound(w, r)
	}
}

func main() {
	srv := &http.Server{
		Addr:         ":8080",
		Handler:      http.HandlerFunc(handler),
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
	}

	log.Fatal(srv.ListenAndServe())
}
// разница в одной букве

http.HandleFunc — регистрирует маршрут на глобальном DefaultServeMux. http.HandlerFunc — конкретный тип-обёртка (func(w, r) с методом ServeHTTP), превращающий обычную функцию в хендлер. Первая — «повесь на URL», вторая — «сделай хендлером».

Можно уйти и глубже, приняв голый net.Listener:

main.gogo
ln, err := net.Listen("tcp", ":8080")
if err != nil {
	log.Fatal(err)
}

srv := &http.Server{Handler: http.HandlerFunc(handler)}
log.Fatal(srv.Serve(ln))

А логику удобно собирать в структуру, реализующую ServeHTTP самостоятельно:

main.gogo
type App struct{}

func (a *App) home(w http.ResponseWriter, r *http.Request)  { fmt.Fprintln(w, "главная") }
func (a *App) about(w http.ResponseWriter, r *http.Request) { fmt.Fprintln(w, "о проекте") }

func (a *App) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	switch r.URL.Path {
	case "/":
		a.home(w, r)
	case "/about":
		a.about(w, r)
	default:
		http.NotFound(w, r)
	}
}

func main() {
	app := &App{}
	srv := &http.Server{Addr: ":8080", Handler: app}
	log.Fatal(srv.ListenAndServe())
}

Разбор запросов к серверу

r.Method
строка метода — GET, POST и так далее.
r.URL.Path / r.URL.Query()
путь запроса и его query-параметры — r.URL.Query().Get("done") вернёт строку даже для булевых значений.
r.Header
map[string][]string — конкретный заголовок берётся через r.Header.Get(...).
r.Body
io.ReadCloser — читается только один раз; после чтения (или если оно не планируется) стоит закрыть через defer r.Body.Close().
main.gogo
func weatherHandler(w http.ResponseWriter, r *http.Request) {
	city := r.URL.Query().Get("city") // ?city=...
	if city == "" {
		http.Error(w, "Не указан город", http.StatusBadRequest)
		return
	}
	fmt.Fprintf(w, "Запрошена погода для города: %s", city)
}

http.Error(w, msg, code) одной строкой ставит и статус, и тело с сообщением об ошибке.

// начиная с недавних версий Go

Path-параметры теперь можно объявлять прямо в шаблоне маршрута, вместе с методом:

http.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	if id == "" {
		http.Error(w, "missing id", http.StatusBadRequest)
		return
	}
})

А чтение тела POST-запроса обычно выглядит так:

main.gogo
type createUserReq struct {
	Name  string `json:"name"`
	Email string `json:"email"`
}

func createUser(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "method not allowed", http.StatusMethodNotAllowed)
		return
	}
	defer r.Body.Close()

	var req createUserReq
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields() // Опционально: лишние поля в JSON → ошибка

	if err := dec.Decode(&req); err != nil {
		http.Error(w, "invalid json", http.StatusBadRequest)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]string{
		"ok":    "true",
		"saved": req.Name,
	})
}

Теги структуры снова делают её удобным контейнером для JSON, а defer гарантирует, что соединение освободится и вернётся в пул.

04

Маршрутизация запросов

С ростом числа маршрутов глобальные http.HandleFunc становятся неудобны — особенно если нужно несколько групп маршрутов или серверов. Маршрутизатор по умолчанию в Go — тип *http.ServeMux, сам реализующий http.Handler. Всё, что мы делали через http.HandleFunc, — это работа с его глобальным экземпляром. Можно завести и собственный:

main.gogo
mux := http.NewServeMux()

mux.HandleFunc("/tasks", tasksHandler)         // Список задач
mux.HandleFunc("/tasks/add", addTaskHandler)   // Создание новой задачи
mux.HandleFunc("/tasks/", taskNotFoundHandler) // Обработчик по умолчанию для подмаршрутов

http.ListenAndServe(":8080", mux)

Правила сопоставления путей у ServeMux:

1

Побеждает самое длинное совпадение — /tasks/add пойдёт именно в addTaskHandler, а не в обработчик /tasks.

2

Маршрут с завершающим слешем (/tasks/) работает как префикс для всех более длинных путей, не попавших под более точные маршруты — удобно для «не найдено».

3

/ — обработчик по умолчанию, если ничего конкретнее не подошло.

Маршрутизацию удобно вынести в отдельную функцию setupRoutes(). Несколько разных ServeMux тоже допустимы — например, один под API, другой под статику, — но обычно хватает одного.

05

HTTP-клиенты на Go

Сервис нередко сам выступает клиентом — обращаясь к внешнему API или соседнему микросервису. Клиентские функции лежат там же, в net/http: высокоуровневые http.Get/http.Post, либо ручная сборка через http.NewRequest + Client.Do.

main.gogo
func getWeather(city string) (float64, error) {
	coords, exists := cityCoordinates[city]
	if !exists {
		return 0, fmt.Errorf("город не найден")
	}

	baseURL, err := url.Parse("https://api.open-meteo.com/v1/forecast")
	if err != nil {
		return 0, err
	}

	q := url.Values{}
	q.Set("latitude", fmt.Sprintf("%f", coords.Lat))
	q.Set("longitude", fmt.Sprintf("%f", coords.Long))
	q.Set("current_weather", "true")
	baseURL.RawQuery = q.Encode()

	resp, err := http.Get(baseURL.String())
	if err != nil {
		return 0, err
	}
	defer resp.Body.Close()

	var data WeatherResponse
	if err := json.NewDecoder(resp.Body).Decode(&data); err != nil {
		return 0, err
	}
	return data.CurrentWeather.Temperature, nil
}
1

http.Get возвращает ошибку, только если запрос не выполнился вообще (сеть, DNS, тайм-аут). Ответ с кодом 404 или 500 — это не err, а нормальный *http.Response с нужным StatusCode, который стоит проверять отдельно.

2

Всегда закрывай resp.Body через defer сразу после проверки ошибки — иначе соединение зависает и не возвращается в пул.

3

Читать тело можно через io.ReadAll или сразу декодировать: json.NewDecoder(resp.Body).Decode(&obj).

4

Для гибкости — ручная сборка запроса с нужными заголовками через http.NewRequest + http.DefaultClient.Do (или свой http.Client с тайм-аутами и прокси).

main.gogo
req, _ := http.NewRequest("PUT", "http://example.com/resource/42", bodyReader)
req.Header.Set("Authorization", "Bearer TOKEN")
resp, err := http.DefaultClient.Do(req)

http.DefaultClient — это просто готовый &http.Client{}. Свой имеет смысл заводить, когда нужны собственные тайм-ауты или транспорт.

06

Middlewares

Middleware — код, выполняемый до или после основного обработчика: логирование, авторизация, единообразная обработка ошибок, сжатие ответа. В стандартной библиотеке отдельного типа под это нет — но обработчики и так интерфейсы и функции, так что реализовать middleware легко самому: функция принимает один http.Handler и возвращает другой, оборачивающий исходную логику.

main.gogo
func loggingMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Printf("=> %s %s\n", r.Method, r.URL.Path)
		next.ServeHTTP(w, r) // Передаём управление дальше по цепочке
		fmt.Println("<= отправлен ответ клиенту")
	})
}
main.gogo
mux := http.NewServeMux()
// ... регистрация маршрутов ...
loggedMux := loggingMiddleware(mux)
http.ListenAndServe(":8080", loggedMux)
flowchart LR
  REQ["запрос"] --> A["withRequestID"] --> B["withLogging"] --> H["hello()"] --> B2["withLogging
хвост"] --> A2["withRequestID
хвост"] --> RES["ответ"]

Middleware работает слоями «луковицы»: внешний оборачивающий отрабатывает первым на входе и последним на выходе

main.gogo
func withRequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("X-Request-ID", uuid.NewString())
		next.ServeHTTP(w, r)
	})
}

func withLogging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("%s %s (%s)", r.Method, r.URL.Path, time.Since(start))
	})
}

func main() {
	h := withRequestID(withLogging(http.HandlerFunc(hello)))
	http.ListenAndServe(":8080", h)
}

Порядок объявления решает: первым при входе сработает withRequestID, затем withLogging, и только потом сам hello. Такую цепочку удобно собрать через маленький хелпер:

main.gogo
// chain склеивает middleware слева направо: сначала outer, потом inner, потом h
func chain(h http.Handler, middlewares ...func(http.Handler) http.Handler) http.Handler {
	for i := len(middlewares) - 1; i >= 0; i-- {
		h = middlewares[i](h)
	}
	return h
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/", hello)
	root := chain(mux, withLogging, withRequestID)
	log.Fatal(http.ListenAndServe(":8080", root))
}

Помимо стандартной библиотеки, для этого есть и сторонние решения:

chi gorilla/mux gorm (не роутер, но тоже маршрутизирует)

На курсе они не используются, но знать о них стоит для кругозора.

Middleware существует и на стороне клиента — через интерфейс http.RoundTripper. Если http.Client отвечает за удобный API, то RoundTripper контролирует саму отправку запроса и чтение ответа — точка расширения между клиентом и транспортом:

main.gogo
// withAPIKey оборачивает транспорт: перед реальным запросом дописывает заголовок
func withAPIKey(key string, next http.RoundTripper) http.RoundTripper {
	return roundTripperFunc(func(req *http.Request) (*http.Response, error) {
		req = req.Clone(req.Context())
		req.Header.Set("X-API-Key", key)
		return next.RoundTrip(req)
	})
}

type roundTripperFunc func(*http.Request) (*http.Response, error)

func (f roundTripperFunc) RoundTrip(req *http.Request) (*http.Response, error) {
	return f(req)
}

func main() {
	client := &http.Client{
		Timeout:   10 * time.Second,
		Transport: withAPIKey("secret", http.DefaultTransport),
	}

	resp, err := client.Get("https://example.com")
	if err != nil {
		log.Fatal(err)
	}
	defer resp.Body.Close()
	log.Println("status:", resp.Status)
}

Через поле Transport цепочки middleware строятся точно так же, как на сервере — удобно для метрик, логов и общих заголовков на все исходящие запросы.
