01

Что сложного в функциях

Ты уже использовал функции как строительные блоки программ: принимал аргументы, возвращал результаты. Но с функцией в Go можно проделывать вещи поинтереснее — потому что функции здесь объекты первого класса. Это значит, что с ними можно обращаться как с любой переменной: переприсваивать, передавать аргументом, возвращать из другой функции.

main.gogo
func main() {
	p := prints    // Не указываем аргументы — функция присваивается переменной
	fmt.Println(p) // Увидим адрес
}

func prints(str string) {
	fmt.Println(str)
}

Функцию можно присвоить переменной в любом месте и передавать её дальше, не вызывая до нужного момента. А если функция нужна только в одном месте и жить отдельной сущностью ей незачем — на помощь приходят анонимные функции: рождаются прямо там, где нужны, без имени, но обязательно с присвоением переменной.

main.gogo
f := func(a int, b int) int {
	return a + b
}

result := f(2, 3)
fmt.Println(result) // 5

Два отличия от обычных функций: нет имени, объявление прямо в коде. А ещё анонимную функцию можно вызвать сразу же, присвоив результат переменной:

main.gogo
result := func(x int) int {
	return x * x
}(4)

fmt.Println(result) // 16

Такие функции нужны в основном для трёх вещей: замыканий, колбэков и локальной логики в конкурентном коде. Сейчас — только про первое.

Замыкания

Замыкание (closure) — анонимная (чаще всего) или именованная функция, использующая переменные из внешней области видимости. Замыкание не копирует значение переменной — оно захватывает её и влияет на её состояние всё время своей жизни.

main.gogo
func counter() func() int {
	i := 0

	return func() int {
		i++
		return i
	}
}

Анонимная функция возвращается из counter, но её тело ссылается на i, объявленную снаружи. Обе находятся в одной области видимости, поэтому анонимная функция видит и удерживает i.

main.gogo
c := counter()

fmt.Println(c()) // 1
fmt.Println(c()) // 2
fmt.Println(c()) // 3
flowchart LR
  subgraph C1["c := counter()"]
    I1["i = 0 → 1 → 2 → 3"]
  end
  subgraph C2["c2 := counter()"]
    I2["i = 0 → 1 → 2"]
  end
  C1 -. "своё, изолированное состояние" .- C2

Каждый вызов counter() порождает новое, независимое замыкание — своё i у каждого

Можно вызвать counter несколько раз подряд и получить несколько разных замыканий — они работают полностью независимо друг от друга. Замыкания захватывают не только переменные, но и параметры функции:

main.gogo
func multiplier(factor int) func(int) int {
	return func(x int) int {
		return x * factor
	}
}

double := multiplier(2)
triple := multiplier(3)

fmt.Println(double(5)) // 10
fmt.Println(triple(5)) // 15

Именованный возврат

Переменные для возврата необязательно создавать в теле функции — можно объявить их прямо в сигнатуре, тогда они появятся уже на этапе компиляции:

main.gogo
func calc(first int, second int) (int, int) {
	sum := first + second
	product := first * second

	return sum, product
}

func calc(first int, second int) (sum int, product int) {
	sum = first + second
	product = first * second

	return
}
// главное правило

Код должен быть понятен тому, кто его читает. Именованный возврат хорош для маленьких функций, но плох там, где логики много или функция не умещается на экран — придётся постоянно возвращаться взглядом к сигнатуре, чтобы вспомнить, что там возвращается.

02

Структуры: группировка данных и никакого ООП

Структура — составной тип, объединяющий связанные переменные в одну единицу данных: именованные поля одного или разных типов в общем контейнере.

main.gogo
type Employee struct {
	Name     string
	Age      int
	Position string
	Salary   int
}

Имя структуры — часть её типа. Создать структуру можно по-разному. Через явное именование полей (пропущенные поля получат zero value своего типа, или nil для ссылочных):

main.gogo
emp1 := Employee{
	Name:     "Анна Иванова",
	Age:      28,
	Position: "Разработчик",
	Salary:   120000,
}

В краткой форме — без имён полей, но строго по порядку:

main.gogo
emp2 := Employee{"Петр Петров", 32, "Тестировщик", 100000}

Или создать пустую (все поля — zero value) и заполнять по мере надобности, обращаясь через точку:

main.gogo
var emp3 Employee
emp3.Name = "Мария Сидорова"
emp3.Age = 25
emp3.Position = "Аналитик"
emp3.Salary = 110000

fmt.Println(emp3.Name) // Мария Сидорова

Важные особенности структур

1

Передача по значению. Как и любой тип, структура передаётся в функцию копией — изменения внутри функции снаружи не видны. Чтобы изменить оригинал, либо явно возвращай структуру, либо передавай указатель на неё.

2

Композиция и встраивание. Структуры можно вкладывать друг в друга (nested-структуры), а частный случай — встраивание (embedding) без имени поля: тогда поля и методы встроенной структуры «продвигаются» и доступны напрямую.

3

Сравниваемость. Структуры сравнимы через ==/!=, только если сравнимы все их поля. Одно поле-слайс — и вся структура теряет сравниваемость.

main.gogo
// Эта функция НЕ изменит оригинальную структуру!
func tryToIncreaseSalary(emp Employee, amount int) {
	emp.Salary += amount // Изменяем только копию
	fmt.Printf("Внутри функции зарплата: %d\n", emp.Salary)
}

// Эта функция изменит оригинальную структуру
func increaseSalary(emp *Employee, amount int) {
	emp.Salary += amount // Изменяем оригинал через указатель
}
// trade-off

Идиоматично передавать по значению, но большие структуры (условно, от ~10 МБ) дорого копировать — тут лучше указатель. А передача по значению гарантирует, что функция не изменит структуру без спроса. Выбирай осознанно.

Композиция — поля любого типа, включая другие структуры:

main.gogo
type Address struct {
	Street string
	City   string
	Zip    string
}

type Person struct {
	Name    string
	Age     int
	Address Address // Вложенная структура
}

Встраивание (embedding) — частный случай композиции, где у поля нет имени. Тогда поля и методы встроенной структуры доступны напрямую, без явного обращения к ней:

main.gogo
type Contact struct {
	Email string
	Phone string
}

type Employee struct {
	Name     string
	Position string
	Contact  // Встроенная структура (анонимное поле)
}

func main() {
	emp := Employee{
		Name:     "Анна Иванова",
		Position: "Разработчик",
		Contact: Contact{
			Email: "anna@company.com",
			Phone: "+7-123-456-7890",
		},
	}

	fmt.Println(emp.Email)         // короткий синтаксис — работает
	fmt.Println(emp.Contact.Email) // полный синтаксис — тоже работает
}
// не наследование

Соблазн назвать это наследованием, как в ООП, — ложный. Вместо отношения «является» (is-a) здесь отношение «содержит» (has-a) с удобным синтаксисом доступа.

При совпадении имён полей возникает конфликт — и тут действуют чёткие правила приоритета:

a

Поле, объявленное в самой структуре, всегда приоритетнее одноимённого поля встроенной.

b

Если совпадение только среди встроенных структур — побеждает поле с меньшей глубиной (ближе к внешней структуре).

c

Если совпадение на одной и той же глубине сразу у нескольких встраиваний — обращение без полного пути даёт ошибку компиляции из-за неоднозначности.

03

Кастомные типы

Поверх любого существующего типа в Go можно объявить собственный — кастомный тип:

main.gogo
type Stringz []string
type Address string
type FullAddress Address
type EveryDay int

Тип можно построить и поверх встроенного (даже массива или слайса), и поверх другого кастомного типа. Это удобно, когда нужно отличать конкретные бизнес-сущности от встроенных типов — или прикрутить к типу собственное поведение, о чём и пойдёт речь дальше.

04

Методы структур

Метод — функция, принадлежащая конкретному типу (структуре или кастомному типу) и реализующая логику, связанную только с ним. Принадлежность обозначается ресивером (получателем) между func и именем функции:

main.gogo
type Status string // Кастомный тип

// s — ресивер типа Status, связывает метод и тип
func (s Status) String() string {
	return string(s) // Приведение к базовому типу
}
main.gogo
type Rectangle struct {
	Width  float64
	Height float64
}

// Получатель по значению
func (r Rectangle) Area() float64 {
	return r.Width * r.Height
}

// Получатель по указателю
func (r *Rectangle) Scale(factor float64) {
	r.Width *= factor
	r.Height *= factor
}

func main() {
	rect := Rectangle{Width: 10, Height: 5}

	fmt.Println("Площадь:", rect.Area())
	rect.Scale(2)
	fmt.Println("После масштабирования:", rect)
	fmt.Println("Новая площадь:", rect.Area())
}

Получатель по значению vs по указателю

По значению — метод получает копию

  • Когда менять поля структуры не требуется
  • Безопасен при конкурентном доступе
  • Может быть дороже — из-за копирования больших структур

По указателю — метод получает указатель

  • Когда нужно менять исходные поля структуры
  • Не копирует — эффективен для больших структур
  • Требует осторожности при конкурентном доступе
// правило согласованности

Указательный ресивер стоит заводить только тогда, когда получателя действительно нужно менять. Но как только он появился у одного метода типа — стоит перевести на указатель и остальные методы. Иначе теряется консистентность, ожидаемая изменяемость и ломается набор методов, нужный для реализации интерфейсов одним типом ресивера.

Публичные и приватные методы

Как и у функций, регистр первой буквы решает: с заглавной — метод экспортируемый (публичный API типа, доступен другим пакетам), с маленькой — неэкспортируемый (внутренняя логика, скрытая от внешнего мира). Это позволяет менять реализацию, не ломая код, завязанный на публичный интерфейс структуры.

Конфликт методов при embedding

1

Продвижение методов. Методы встроенной структуры автоматически становятся доступны у внешней.

2

Приоритет внешней. Метод внешнего типа скрывает одноимённый метод встроенной структуры.

3

Неоднозначность. Если два встроенных типа на одной глубине делят одно имя метода — вызов без уточнения (fh.Write()) — ошибка компиляции. Нужен явный путь.

05

Интерфейсы: определение поведения

Интерфейс в Go — абстрактный тип, описывающий поведение через набор методов, а не данные. Правило языка — утиная типизация: если что-то ходит как утка, крякает как утка и летает как утка — это утка. На практике: если тип реализует все методы интерфейса, он автоматически ему удовлетворяет — без явного implements.

main.gogo
type Shape interface { // Два метода в контракте
	Area() float64
	Perimeter() float64
}

type Rectangle struct { // Реализует Shape, хотя методов три, а не два
	Width  float64
	Height float64
}

func (r Rectangle) Area() float64      { return r.Width * r.Height }
func (r Rectangle) Perimeter() float64 { return 2 * (r.Width + r.Height) }
func (r Rectangle) Info() {
	fmt.Println("Width: ", r.Width)
	fmt.Println("Height: ", r.Height)
}

Использование интерфейсов

Практическая польза — минимум в двух вещах: избавление кода от конкретных зависимостей и, как следствие, простота тестирования. Функция, принимающая интерфейс, зависит не от реализации, а от поведения:

main.gogo
func printShapeInfo(s Shape) {
	fmt.Printf("Площадь: %.2f\n", s.Area())
	fmt.Printf("Периметр: %.2f\n", s.Perimeter())
}

func main() {
	rect := Rectangle{Width: 10, Height: 5}
	circle := Circle{Radius: 3}

	printShapeInfo(rect)   // Один и тот же код
	printShapeInfo(circle) // работает с разными типами
}

Оба поля интерфейса — указатели: один на метаданные о типах и методах, второй — на само значение

Пустой интерфейс

Пустой интерфейс interface{} (с Go 1.18+ — any) не требует ни одного метода. А раз любой тип может иметь ноль методов — любой тип удовлетворяет пустому интерфейсу. Это делает any универсальным контейнером для значения любого типа:

main.gogo
func printAnything(value interface{}) {
	fmt.Printf("Значение: %v, Тип: %T\n", value, value)
}

func main() {
	printAnything(42)                              // int
	printAnything("Hello")                         // string
	printAnything([]int{1, 2, 3})                  // []int
	printAnything(Rectangle{Width: 10, Height: 5}) // Rectangle
	printAnything(nil)                             // 
}

В исходниках пустой интерфейс — тоже отдельная, более простая структура (исходник) — без таблицы методов itab, потому что проверять соответствие набору методов не нужно:

runtime2.gogo
type eface struct {
	_type *_type
	data  unsafe.Pointer
}

Type Assertion

Чтобы извлечь конкретный тип из значения интерфейса — type assertion, с проверкой через идиому «comma, ok»:

main.gogo
func processValue(value interface{}) {
	if str, ok := value.(string); ok {
		fmt.Printf("Это строка: %s (длина: %d)\n", str, len(str))
	} else if num, ok := value.(int); ok {
		fmt.Printf("Это число: %d (квадрат: %d)\n", num, num*num)
	} else {
		fmt.Println("Неизвестный тип")
	}
}

Type Switch

Более элегантный способ работы с разными типами:

main.gogo
func describe(value interface{}) {
	switch v := value.(type) {
	case string:
		fmt.Printf("Строка длиной %d: %s\n", len(v), v)
	case int:
		fmt.Printf("Целое число: %d\n", v)
	case float64:
		fmt.Printf("Число с плавающей точкой: %.2f\n", v)
	case Rectangle:
		fmt.Printf("Прямоугольник: площадь = %.2f\n", v.Area())
	default:
		fmt.Printf("Неизвестный тип: %T\n", v)
	}
}

Ограничения и особенности пустого интерфейса

1

Потеря статической типизации. var x any = 42; x + 10 — ошибка компиляции: Go не знает, что x число. Нужен явный type assertion.

2

Производительность. Проверка и приведение типов на каждый элемент — заметно медленнее, чем работа с уже конкретным типом.

3

Нет проверки на этапе компиляции. data.(int) для строки внутри any благополучно скомпилируется — и упадёт паникой в рантайме. Безопасный путь — снова «comma, ok».

main.gogo
// Медленнее — нужны проверка типов и приведения
func slowSum(values []any) int {
	sum := 0
	for _, v := range values {
		if num, ok := v.(int); ok {
			sum += num
		}
	}
	return sum
}

// Быстрее — работа с конкретным типом
func fastSum(values []int) int {
	sum := 0
	for _, v := range values {
		sum += v
	}
	return sum
}

Пустой и nil-интерфейс

Их часто путают — но это не одно и то же. Пустой интерфейс не имеет набора методов, но вовсе не обязан быть nil. nil означает, что интерфейс инициализирован как тип, но не содержит значения, которому можно сопоставить удовлетворение поведению:

main.gogo
func main() {
	var p fmt.Stringer
	var i any

	fmt.Println(p == nil) // true
	fmt.Println(i == nil) // true

	i = 42
	fmt.Println(i == nil) // false
}

Method set и правила реализации интерфейсов

Method set — набор методов, доступных значению конкретного типа. От него напрямую зависит, какой тип какому интерфейсу может удовлетворять:

Метод объявлен какВходит в method set типа TВходит в method set типа *T
(t T) — по значениюдада
(t *T) — по указателюнетда
main.gogo
type Document struct {
	title   string
	content string
}

func (d Document) GetTitle() string    { return d.title }
func (d *Document) SetTitle(title string) { d.title = title }

type Reader interface { GetTitle() string }
type Writer interface {
	GetTitle() string
	SetTitle(string)
}

func main() {
	doc := Document{title: "Заголовок", content: "Содержимое"}
	docPtr := &Document{title: "Заголовок", content: "Содержимое"}

	var r1 Reader = doc    // OK
	var r2 Reader = docPtr // OK — указатель включает и методы значения

	var w1 Writer = doc    // Ошибка компиляции: method set T не включает SetTitle
	var w2 Writer = docPtr // OK
}

Автоматическое разыменование

При вызове метода Go сам преобразует между указателем и значением:

main.gogo
type Counter struct {
	value int
}

func (c *Counter) Increment() { c.value++ }
func (c Counter) GetValue() int { return c.value }

func main() {
	counter1 := Counter{value: 0}
	counter1.Increment() // компилятор подставит (&counter1).Increment()

	counter2 := &Counter{value: 0}
	value := counter2.GetValue() // компилятор подставит (*counter2).GetValue()

	fmt.Println(counter1.GetValue(), value)
}
// но не при интерфейсах

Авторазыменование работает только в момент вызова метода — оно не меняет сам method set типа. При присваивании интерфейсу учитывается именно исходный method set, а автоматической подстановки уже не будет.

Композиция интерфейсов

Интерфейсы комбинируются в более сложные контракты — точно так же, как структуры:

main.gogo
type Reader interface { Read([]byte) (int, error) }
type Writer interface { Write([]byte) (int, error) }
type Closer interface { Close() error }

type ReadWriter interface {
	Reader
	Writer
}

type ReadWriteCloser interface {
	Reader
	Writer
	Closer
}

Идиомы проектирования интерфейсов

1

Держи интерфейсы маленькими. Лучше много маленьких, чем один большой.

2

Определяй там, где используешь — не в пакете с реализацией. Интерфейс отражает потребности клиента, а не возможности провайдера.

3

Осмысленные имена — Writer, Reader, Validator.

4

Принимай интерфейсы — возвращай конкретные типы. Абстракция нужна там, где ты потребляешь поведение; вызывающему полезны реальные поля и методы результата.

5

Не вводи интерфейс «на всякий случай». Одна реализация без потребности в подмене — начинай с конкретного типа. Интерфейс добавь, когда появится реальная вариативность.
